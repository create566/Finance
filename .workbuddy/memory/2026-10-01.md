## 补下架闭环（P0 真缺口，已完成并通过单测）

**问题**：`LendServiceImpl.offline()` 原先只 `lend.setStatus(OFFLINE)` + `evictAll()`，
不退还已投资金、不作废合同、不发通知 → 标的被下架后投资人资金一直冻在银行侧，双方都不知情。

**改法**（复用 `failLend()` 已有实现，不新写资金逻辑）：
- `LendServiceImpl` 抽出私有方法 `withdrawAllInvestments(Lend)`：把该标 `lend_item.status=0` 批量置 1、
  清零 `lend.invest_amount`、`redisTemplate.delete("lend:leftAmount:"+lendId)`，返回被撤记录供调用方发通知。
  `failLend()` 改为复用它（行为等价，并补上了它一直缺的 Redis 缓存清理）。
  为此 `LendServiceImpl` 新增注入 `RedisTemplate` 与常量 `LEFT_AMOUNT_KEY`（与 `LendItemServiceImpl` 同 key）。
- 新增 `revokePendingContracts(Lend, String)`：作废该标下 `biz_type='LEND' & biz_id=lendId & status=0` 的合同；
  单份失败只 `log.warn` 不抛出，避免已签合同把整笔下架事务带崩。
- `offline()` 顺序：退资 → 作废合同 → 翻状态+evictAll → 通知借款人 + 每个投资人。

**新增消息类型**：`MessageTypeEnum.LEND_OFFLINE(29, "标的已下架")`
→ 必须同步前端 `ww_finance_user/src/api/message.ts` 的 `MESSAGE_TYPE_META`（漏了消息中心显示空白）。
`message.message_type` 是 TINYINT 无约束，加值安全。

**验证**：新增 `api/src/test/java/com/example/demo/service/impl/LendOfflineClosureTest.java`
（5 用例，纯 Mockito，离线可跑），5/5 绿。覆盖：有投资下架全链路 / 待发布无投资空跑 /
合同作废失败不阻断 / 非法状态拒绝且零副作用 / 标的不存在。

- **Docker Desktop 当前未启动** → Redis `6379` 完全不可达（`ww_redis`/`ww_chroma` 全不可用）。
- `JwtAuthInterceptor` 强依赖 Redis：token 必须 `5grcs ` 前缀，且要与 `login:token:<role>:<userId>`
  的值**完全相等**，命中后还会 `expire` 续期 7 天。Redis 挂了连 401 之外的状态都拿不到。
- 结论：**Redis 未起时无法做端到端 HTTP 验证**。下架新引入的 `redisTemplate.delete`
  与投标 / `cancelInvest` 一样，把 Redis 变成了硬依赖。

## 全量代码审计 → 分 5 批修复 bug（进行中）

审计结论：4 个 P0 / 4 个 P1 / 若干 P2。**每个 P0/P1 都人工复核过**（扫描器有假阳性：
`UserChatController.closeSession` 被报"缺登录校验"，实际它调 `checkOwnSession(id)` 内部已做
`LoginUserContext.getUserid()` + 归属校验）。修复顺序：按"资金风险 × 修复成本"分 5 批。

### 第 1 批（已完成）：假 404 + 越权
- **① `makeLoan` 后端接口被前端"打错地址"**：管理端 `ww_finance_admin/src/api/loanProject.ts`
  原先请求 `/loan/${id}/makeLoan`，而真实映射是类级 `@RequestMapping("/admin/core/loan/project")`
  + `@PutMapping("/{id}/makeLoan")` → 改成 `/loan/project/${id}/makeLoan`。
- **③ 还款明细接口越权（IDOR）**：`LendReturnController.itemReturns` 原先不取当前登录人，
  任何人传 `lendReturnId` 都能看到全部投资人的回款明细。改法：`LoginUserContext.getUserid()`
  为空直接 401；`LendReturnServiceImpl.listItemReturns(lendReturnId, userId)` 先查 `LendReturn`，
  不存在抛 `ResourceNotFoundException(404,"还款计划不存在")`；**非借款人**追加
  `wrapper.eq(LendItemReturn::getInvestUserId, userId)`（压到 SQL 层过滤），借款人看全部。

### 第 2 批（已完成）：配置泄露 + 密钥双源
- **② 生产凭据硬编码**：`api/src/main/resources/application.yml` 里 bank-datasource 曾写死
  RDS 公网地址 + 明文口令 `shangqiuedu/shangqiuedu_kakdadajeLo90` → 全改
  `${BANK_DB_URL:...}` / `${BANK_DB_USERNAME:...}` / `${BANK_DB_PASSWORD:...}`，默认值与历史一致。
- **⑥ JWT 密钥双源（最危险的一处）**：`TokenUtil.secret` 是 `private final static` 硬编码，
  yml 里的 `security.jwt.secret` 根本没人读 —— 改 yml 会**看起来生效、实际无效**。
  改法：`TokenUtil.secret` 去掉 final + 加 `setSecret()`；新增
  `api/.../config/JwtSecretConfig.java`（`@Value("${security.jwt.secret:...}")` → `setSecret`）。
  ⚠️ **yml 默认值必须保持历史的 `vsofo-5grcs-secret`**（原 yml 里写的是
  `vsofo-5grcs-secret-change-me`，若拿它当默认会让**线上所有 token 立刻失效、全员被登出**）。
  配 `TokenUtilTest`(5) 把"旧密钥签出的 token 仍可解析"钉死。
  （另：jjwt 0.9.1 的 `signWith(HS512, String)` 会先对密钥做一次 base64 解码，自签测试 token 要注意。）

### 第 3 批（已完成）：事务内吞异常（造成"静默部分提交"）
共性模式：方法上写了 `@Transactional(rollbackFor=Exception.class)`，方法体却整段包在
`try{...}catch(Exception e){log.error}` 里 → **异常被吞 = 事务不回滚 = 已写的部分数据被提交**。
- **④ `LendReturnServiceImpl` 还款回调**：结算记录（`LendSettleRecord`）+ 站内信 + 积分
  三件事被一个 catch 包住，失败只打日志 → 还款主事务照常提交，**清算记录丢失、积分漏加**。
  已移除该 catch，让失败在事务内抛出整体回滚，靠银行侧重试。
  （`addIntegral`、`message.send` 都在同一事务里，内层标记 rollback-only，外层提交必抛
  `UnexpectedRollbackException` —— 这也反证了"必须整体回滚"而不是吞掉。）
- **⑤ `LendSettleRecordServiceImpl` 前置加固**：`createSettleRecord` 捕获
  `DuplicateKeyException` 做幂等（并发/重试下不炸）；`getByLendId` 由 `getOne(...)` 改
  `getOne(..., .last("LIMIT 1"))`，脏数据下不再抛 `TooManyResultsException`。
  （需 `uk_lend_id` 唯一索引才算真幂等，列为后续迁移项。）
- **⑧ `ReconciliationServiceImpl.reconcileWithBank`**：整个对账体包在 catch 里，
  而 `reconciliation_record` 的 `trans_no/trans_type/user_id/amount/status` **全是 NOT NULL**，
  代码里 `Integer.parseInt(bankFlow.get("type").toString())` 这类写法银行少回一个字段就 NPE →
  NPE 被吞 → 差异记录**写一半提交、调用方只看到"对账异常"文案**。改法：
  1. 删掉外层 catch，异常直接上抛触发回滚（调用方 `FinanceJobHandler.dailyReconciliation`
     本就有 try/catch + 日志）；
  2. 银行字段全部走 null 安全解析（`str/parseAmount/parseInt/parseLong`），缺失落占位值
     （0 / 0L / 0.00），保证 NOT NULL 可写；
  3. 缺 `transNo` 的银行流水**不落库**，单独计 `无法比对` 笔数（没有主键的差异记录没有可操作性）；
  4. `TransTypeEnum.fromCode` 遇未知码会抛 `IllegalArgumentException`（与 `ContractStatusEnum`
     返回 null 语义相反）→ 换成不抛的 `typeNameOf()`，未知码显示 `未知类型(99)`。
  5. 顺带把 Iterator 手写匹配换成 `localFlowMap.remove(transNo)`；新增 `abnormalCount` 进 summary。
  **新增 `ReconciliationServiceImplTest`(8 用例)**，钉住三条不变量：异常必须上抛且零落库 /
  字段缺失不 NPE / 缺 transNo 只计数不落库。
