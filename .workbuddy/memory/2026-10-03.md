## 第 4 批：并发加固（⑤⑦）

### ⑤ 投标的「空转锁」——删掉，不是换新锁
`LendItemServiceImpl.buildInvestForm` 原先取 `lend:leftAmount:<lendId>:lock` 的 Redis 锁，
锁内只做一次"重新查银行余额"的**只读**操作。三个独立缺陷叠在一起：
1. `buildInvestForm` **不写任何库、也没 `@Transactional`** → 互斥保护不了任何东西；
2. 锁 key 按**标的**加锁，却当成"防同一用户重复提交"在用 → 同一标的上并发投标的
   **不同用户会互相顶掉**，误报"请勿重复提交"（热门标的必现）；
3. `unlock(key)` 不校验持有者 → A 能删掉 B 持有的锁（经典锁 bug）。

**结论：这锁既没用还有害，直接移除**。真正的防超募闸门是回调里的
`baseMapper.atomicInvest`（条件 UPDATE `WHERE amount - invest_amount >= ?`，靠数据库行锁），
在代码注释里把这一点写明。顺带修掉 `if (lend.getUserId() != null)`（借款人恒非空 →
Redis 缓存判断必被 DB 值覆盖，缓存形同虚设）与 `lend.getAmount()` 的 NPE 风险。

⚠️ **仍存在的真缺口（本次没修，需银行协议支持）**：两阶段设计（下单→银行冻结→回调）下，
若回调时 `atomicInvest` 返回 0（标的已满），平台 `return true` 应答成功，
**用户的钱已在银行侧冻结却没有对应投资记录 → 资金挂账**。要修必须调银行的"撤销投标/解冻"接口，
而 `HfbConst` 里**没有**这个端点。已在报告中标注为后续项。

### ⑦ 提现闸门：可用余额必须扣掉「在途」提现
`UserAccountServiceImpl.buildWithdrawForm` 原先只比**银行余额**。但银行余额要等回调才减少，
用户没走完银行页面之前那条流水一直是 `PROCESSING`：
`余额 1000 → 提 1000（受理）→ 再提 1000（又受理）` —— 同一笔钱重复提交两次，
**不需要并发、连点两下就能触发**。

修法：`可用余额 = 银行余额 − Σ(处理中提现)`。
- 新增 `TransFlowMapper.sumAmount(userId, transType, status)`（显式 `@Select`）。
  **手写注解 SQL 必须显式写 `is_deleted = 0`**：`@TableLogic` 的自动过滤只对 MP 生成的 SQL 生效，
  注解 SQL 不会被追加。
- 单独给"被在途占满"一个可解释的文案（否则用户看到"当前可用 ¥0"而余额明明是 1000 会以为有 bug）。
- 提现**失败**回调会把流水置 FAILED，占用随之释放；成功回调时银行余额也已同步减少，不会重复扣。
- 用真实 MySQL 校验了 SQL 语法，并**实测到用户 33 有一笔 ¥1000 的处理中提现** ——
  正好是旧逻辑会漏算的那笔。
