## 完成：满标后超期未签《放款确认书》的自动退资定时任务

资金悬停的最后一块拼图。此前只有"满标催签站内信 + 管理端人工退资出口"，
现在补上系统自动处置，三条措施齐了：催签 → 人工出口 → **自动超期处置**。

### 关键设计：起算点不能用 update_time
标的满标时原本**只写 update_time**，而该列是 `on update CURRENT_TIMESTAMP` ——
放款写 payment_time、下架写 offline_time、后台任何一次编辑都会覆盖它。
拿它当宽限期起算点 = **动一下记录就重置宽限，借款人拖着不签反而能无限续期**。
⇒ 新增 `lend.complete_time`（`sql/lend_complete_time.sql`，幂等 + 回填历史数据），
只在满标那一刻写一次。`LendItemServiceImpl` 满标分支显式 `setCompleteTime(now)`。
⚠️ 定时任务查询条件 `.isNotNull(Lend::getCompleteTime)`：起算点不明就动投资人资金，
风险远大于收益，宁可留着让人工在管理端判断。

### 定时任务（FinanceJobHandler#refundUnsignedCompletedLends，cron 每天 01:30）
三个**防误伤边界**，漏一条就会退掉本该正常放款的标的：
1. 起算点用 complete_time，不是 update_time（见上）
2. **《放款确认书》已签则跳过** —— 已签但运营还没点放款属正常待放款，不能退资
3. **payment_admin_id 非空则跳过** —— 钱在路上，退资会导致账目错乱

宽限期常量 `LendService.MAKE_LOAN_SIGN_DEADLINE_DAYS = 3`，
⚠️ **必须与合同模板 TPL_LOAN / TPL_INVEST 里的条款天数一致** —— 代码写 7 天、合同写 3 天，
处置行为就失去合同依据。改一处要同时改另一处。

### 系统处置通道：offlineBySystem vs offline
拆成 `offlineInternal(lendId, adminId)` 核心 + 两个入口：
- `offline(lendId, adminId)`：人工，**adminId 为 null 直接拒绝**
- `offlineBySystem(lendId)`：定时任务，adminId=null → `offline_admin_id` 落 NULL

**没有**放宽 offline() 让它接受 null —— 两个入口的语义不能混，人工通道必须持续保证"有操作人"。
落 NULL 正好对应前端已有的"系统自动处置"显示（status=4 + offlineAdminName 为空）。

### 消息类型 31：MAKE_LOAN_TIMEOUT「超期未签已退款」
不给投资人发 LEND_OFFLINE(29)"标的已下架" —— 钱退回来了却收到"下架"，用户会莫名其妙。
新增 `MessageTypeEnum.MAKE_LOAN_TIMEOUT(31)` + `MessageService` 两个方法（借款人/投资人各一），
前端 `ww_finance_user/src/api/message.ts` 的 `MESSAGE_TYPE_META` 同步加 31。
⚠️ 消息类型加值必须同时改 Java 枚举 + 前端映射，忘了消息中心显示空白。

### 自动获取 token 的两个关键（写错就死循环或不生效）
1. **集合级 Pre-request 必须排除 `/login`、`/register`、`/sendCode`** ——
   否则登录请求自身触发"取 token → 去登录"的无限递归。
2. **两端 token 不能混用**：`JwtAuthInterceptor` 按 role 校验，
   admin 角色访问 `/api/**` → 403，user 角色访问 `/admin/**` → 403。
   管理端发 `token` 头，用户端发 `Authorization` 头。
   登录返回的 `data` **已带 `5grcs ` 前缀**（`TokenUtil.generate*Token` 拼的），直接用即可。
