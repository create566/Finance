## 架构决策：三方案对比，结论选「保持现状 + 定向加固」

## 平台资金 / 收费链路专项审计（字节码 + 银行库实证）

起因：确认"平台怎么管理资金？平台不能控制资金，只能赚服务费（银行返点）"这一模式在本工程里到底怎么落地的。

方法：`javap -p -c` 反编译 `ww_bank_tmp/BOOT-INF/classes`（与 `ww_bank-1.0.0.jar` md5 一致）关键类；
直连 RDS `ww_bank` 查全部 5 张表。结论已沉淀进 MEMORY.md「平台收费」节，此处记过程与未决项。

- **银行库只有 5 表，没有平台/商户账户表**：user_account(user_code=bindCode)/user_bind/user_invest/user_return/user_item_return。
  服务费只以字段留痕（`user_return.vote_fee_amt`、`user_invest.vote_fee_amt`、`user_item_return.fee_amt`），**不划转到任何账户** ——
  即"银行返点"在系统里只是账面条目，钱实际留存在银行清算账户，靠线下结算。
- **两个收费口（逐条字节码确认）**：
  ① 放款 `UserInvestServiceImpl.makeLoan`：解冻各投资人 `voteAmt` → `mchFee=new BigDecimal(map.get("mchFee"))` →
  `transferAccounts(benefitBindCode, ΣvoteAmt − mchFee)` ⇒ 借款人实收 = 募资额 − 平台服务费（砍头息式）；`user_invest.status==1` 幂等直接返回。
  ② 还款 `LendReturnServiceImpl.returnCommit`：遍历 data 给每个投资人 `transferAccounts(toBindCode, transitAmt)` 并累加 →
  **强校验 `voteFeeAmt + ΣtransitAmt == totalAmt`**（不等抛 `HfbException(RETURN_AMMOUNT_MORE_ERROR)`）→
  `transferAccounts(fromBindCode, "-"+totalAmt)` 扣借款人 ⇒ 投资人拿全额本息，`voteFeeAmt` 即平台服务费。
- **平台侧现状：服务费一分未收**。`lend_return.fee` / `lend_item_return.fee` 在 `handleMakeLoanNotify` 硬编码 `BigDecimal.ZERO`；
  投标 `buildInvestForm` 传 `voteFeeAmt="0"`；`lend.service_rate`（DB 有字段、注释写"平台服务费率"）**全项目零引用**（死字段）；
  平台代码**无 `mchFee` 字面量**（从不传）→ 银行 makeLoan 读它必 NPE，且发生在**解冻投资人资金之后**（危险顺序）。
- **银行只有 4 类异步回调**（UserBind / UserAccount 充值+提现 / UserInvest 投标 / LendReturn 还款），
  **没有"放款回调"** → 平台 `/api/core/lend/notifyMakeLoan` 不会被这个 jar 触发（现有 4 个已放款标的 `payment_admin_id` 全 NULL，
  与"没走管理员放款按钮、靠注入/历史数据"一致）。
- **逾期还款必失败**：逾期时平台传 `totalAmt = 本息 + 罚息`，而 voteFeeAmt=0、ΣtransitAmt=本息 → 银行等式不成立。
  代码注释写"罚息部分归平台"，但要用上这条通道必须把 `fee` 落成罚息。
- 实证数据：银行侧 user_invest 71 笔 Σvote 1509.3 万、user_return 62 笔、user_item_return 125 笔，fee 字段**全 0**；
  平台 `lend_return` 48 行 fee**全 0**。
- **未决 / 需实测**：mchFee 缺失导致的 NPE、放款回调缺失，这两条是**静态字节码推断**（银行 jar 无源码、不修改），
  未做端到端复现；若要给出确定结论，需在 9090 + 8991 都起来时用真实标的跑一遍放款并抓银行侧 stdout。

## 项目现存问题盘点（2026-10-08 全量核查）

复核手段：`netstat` 看运行集 + 平台库直查（lend/lend_item/lend_return/trans_flow/contract/user_bind/user_account）+

### P0 资金与账实
1. **银行侧 3 个账户余额为负**：-100.00、-650.60、-1,308,223.87（共 139 个账户）。原因：银行 `transferAccounts` 是无条件加减，

## api ↔ finance-oss 重复代码审计（用户提问，只读）

**结论：确有重复，分三层。**

### 甲、类名完全相同的 4 个（comm 交集实测）
`JwtAuthInterceptor` / `TokenUtil` / `LoginUserContext` / `JwtSecretConfig`
- `LoginUserContext`：api 47 行 vs oss 52 行，**代码体逐行相同**，只差 5 行 javadoc。纯复制。
- `TokenUtil`：`secret` 字段 / `setSecret` / `getClaimsFromToken` / `getMapInfoFromToken` **同构**；
  oss 是 api 的**真子集**（api 多 `generateMerchantToken`/`generateAdminToken`/`isTokenExpired`/`expiration`）。
  微差：oss 的 `getMapInfoFromToken` 先判 `token==null`，api 版没有（api 靠拦截器先判空）。
- `JwtAuthInterceptor`：取 token→判 `5grcs `→`TokenUtil` 解析→`login:token:<role>:<id>` **值完全相等**→
  `expire 604800`→写 `LoginUserContext`→admin 拒绝 403，这一整条链**两边同构（~80%）**。
  差异：api 多 `/admin/` 路径判定 + 每请求 `log.info` 打 token 头；oss 只服务 `/api/oss/file/**` 故无路径判定。
- `JwtSecretConfig`：构造函数体几乎相同（`@Value("${security.jwt.secret:vsofo-5grcs-secret}")` + 默认值告警）。

### 乙、类名不同但功能重复（同 HTTP 契约 + 同存储逻辑）
- **两个 `@RequestMapping("/api/oss/file")`**：api `OssFileController` ↔ oss `FileController`；
  都 `POST /upload` + `DELETE /remove`；都「401 判空 → 属主编进路径 → 删除 403」，**同路径同动词**。
- **存储实现**：api `LocalFileStorageStrategy` ↔ oss `FileServiceImpl`；
  `deleteOwned` / `isOwnedBy`（三段式 `[category, u<id>, file]`）/ `ownerDir` / `deleteUnchecked` /
  `generateFileName` **逻辑与日志逐字相同**（连注释 `不区分"文件不存在"与"不是你的"` 都一样）。
- **接口**：api `FileStorageStrategy` ↔ oss `FileService`，归属模型（`upload(file,category,ownerId)` /
  `deleteOwned(url,ownerId)`）一模一样。
- ⚠️ **安全强度不一致**：oss 版有 `resolveSafePath()`（normalize + startsWith 防护路径穿越）+
  `validateCategory/validateCustomName`，**api 版没有**，只做字符串拼接 + 前端 `..` 粗检。
  ⇒ 同一能力两份实现，修一边漏一边。
- api 版**多** `upload(byte[],originalName,category)`（`ContractServiceImpl:278` 合同签名存证用），oss 版无 ——
  这正是不能简单删掉 api 那份的原因。

### 丙、跨模块同名但各跑各的（不冲突、属"分裂的两份"）
- `GlobalExceptionHandler` **两份**：api `com.example.demo.common`（8 个 handler）↔
  finance-common `com.wwfinance.common.exception`（6 个 handler），三处语义重叠
  （`Exception`/`ResourceNotFoundException`/`MethodArgumentNotValidException`）。
  **为什么不冲突**：api 主类 `@SpringBootApplication` 无 `@ComponentScan` → 只扫 `com.example.demo` → 用自己那份；
  oss 主类 `@ComponentScan("com.wwfinance")` → 扫到 finance-common 那份。
  finance-common **无 resources/ 目录、无 spring.factories** → 不做自动装配，只能被组件扫描命中。
- `RedisConfig` 同样两份：api `com.example.demo.config`（StringRedisSerializer）↔
  finance-base `com.wwfinance.base.config`（Jackson2Json）。api **源码零引用 `com.wwfinance.base`**（grep 实测空），
  ⇒ api 里那份 finance-base 依赖其实是**死依赖**（只为传递 finance-common）。
- oss 的 `@ComponentScan("com.wwfinance")` 会把 **finance-base 的 `WebMvcConfig`/`Swagger2Config`/`RedisConfig`**
  一并加载进 oss（`Long→String` 序列化等）；该 WebMvcConfig 只加 converter、不加拦截器 → 与 `OssWebConfig` 无冲突。

### 根因与建议（未改任何代码）
- 根因：`finance-common` 早就存在且两模块都依赖，但 `TokenUtil`/`LoginUserContext` 这类纯工具**没放进去**；
  官方解释写在 oss 版注释里 ——「api 那份被大量既有代码静态引用，挪走会波及整个 api 模块」。
- 建议（按性价比）：①`TokenUtil`+`LoginUserContext` 抽进 finance-common（api 调用点全是静态调用，改 import 即可）；
  ②api 的 `LocalFileStorageStrategy` 补 `resolveSafePath`（对齐 oss 的穿越防护，这是**真实安全缺口**）；
  ③存储层维持两份（api=生效实现，oss=预留独立形态），但把归属校验公共逻辑抽成 finance-common 工具类。
- ⚠️ 潜在坑：两个 `/api/oss/file/upload` 同路径 → 经网关（路由 `/api/oss/file/**`→service-oss）只命中 oss，
  api 那份不可达；前端直打 8990 则命中 api 那份。**行为取决于入口**，改前端代理时要意识到这点。

### 结论（已答用户）
1. **4 个同名类（TokenUtil/LoginUserContext/JwtAuthInterceptor/JwtSecretConfig）→ 可删可合并，功能不变**。
   ⚠️ 唯一坑：`JwtSecretConfig` 是 `@Configuration`，抽进 finance-common 后 oss（扫 `com.wwfinance`）自动加载，
   但 **api 不扫 `com.wwfinance`** → 需给 api 加 `@ComponentScan("com.wwfinance.common")` 或在 api 留薄配置。
2. **文件存储 → 不建议删 api 那份**。若为「各司其职」而删：

   - 连存储实现一起删 → **功能会变**：必须新增 api→oss Feign 传 byte[]，且 **oss 挂则合同签不了**
     （把可选模块变成核心链路硬依赖）。
3. 比消重复更该先做的：**api 的 `LocalFileStorageStrategy` 补 `resolveSafePath`**（唯一真实安全缺口）。

## 追问「finance-base 是干啥的」（14:3x，只读核实）

口径：**base = 技术装配层**（Spring 框架配置集中地，零业务逻辑）。6 个类逐条：
- `config/RedisConfig` —— RedisTemplate 序列化（String key + Jackson JSON value + 类型信息 + JavaTimeModule）。
- `config/WebMvcConfig` —— 消息转换器：**Long/BigInteger → String**（防前端 JS 精度丢失）+ LocalDateTime `yyyy-MM-dd HH:mm:ss`。
  ⚠️ 类上注明"不能加 `@EnableWebMvc`"（会关掉 Spring Boot 的 WebMvc 自动配置，影响 oss 上传下载）。
- `config/OpenFeignConfig` —— Feign 日志级别 FULL。
- `config/Swagger2Config` —— Knife4j/Swagger 文档，`adminApi` / `webApi` 两组。
- `config/RedisKeyManage` —— key 常量：`sms:code:`（TTL 5min）、`login:code:`（TTL 2min）。
- `dto/SmsDTO` —— 短信请求体（mobile + message）。
- 🔑 **最反直觉的结论：base 只对 `finance-message` / `finance-oss` 生效，对 `api` 完全不生效。**
  判据 = 启动类包名决定的组件扫描范围：
  - `finance-message`：`com.wwfinance.MessageApplication` → 扫 `com.wwfinance.**` → **含 base** ✓
  - `finance-oss`：`com.wwfinance.oss.OssApplication` + 显式 `@ComponentScan({"com.wwfinance"})` → **含 base** ✓
  - `api`：`com.example.demo.DemoApplication`（无 `scanBasePackages`）→ 只扫 `com.example.demo.**` → **扫不到 base** ✗

## 20:45 P4-53 修复完成 —— 多投资人标的还款已跑通（业务循环闭环）

用户问「【多投资人标的的还款必被银行拒绝】这个咋解决」，实施四层修复并实测通过。

### 根因（比原先判断的更深）
不只是"分厘差 1 分"：
- `ReturnPlanCalculator.buildPlan` 用 `money(principal+interest)` 算 total，而 principal/interest
  各自舍入 ⇒ `p + i ≠ t`（60 期里 22 期）。
- 投资人明细原是**每个投资人独立跑一遍计算器**，等额本息数学可加但各自舍入不可加；
  **末期更严重**（末期本金=剩余本金，误差累积）⇒ 实测标的10 第12期偏差 **0.13 元**，不是 1 分。

### 四层修复
1. **L1 计划口径**（`ReturnPlanCalculator`）：`total = money(p) + money(i)`；等额本息/等额本金
   改为**月供先舍入为权威、本金倒挤**（`principal = 月供 − 利息`），total 恒等于月供不再漂移。
2. **L2 分摊口径**（`bookMakeLoan`）：投资人明细由"独立计算"改为**按投资占比切分期供**
   （`ratio = investAmount / lendAmount`，10 位精度），各期偏差压到 ≤ 0.01×户数。
3. **L3 生成期倒挤**：新增 `balanceItemReturns()`，逐期把差额补到**投资金额最大**的一户，
   保证 Σprincipal/Σinterest/Σtotal 三个都 ≡ 期供。
4. **L4 运行期兜底**（`buildRepayForm`）：自检 `voteFeeAmt + ΣtransitAmt == totalAmt`，
   不等就倒挤到最后一户（存量脏计划也能还）；倒挤出负数则拒绝并留痕。
5. **存量订正**：`sql/fix_repay_plan_balance.sql`（脚本 `.workbuddy/tmp/fix_repay_plan_balance.py`）
   —— 三条集合式 UPDATE：`lend_return.total := p+i`、`lend_item_return.total := p+i`、明细倒挤。
   **只动 status=0 未还期**。订正后期供自洽 0、明细自洽 0。
   ⚠️ 订正顺序有讲究：必须① ②先落库，③再重算（③的查询要基于订正后的值）。

### 顺带修的（同一处代码 / 同一机制）
- **P0-4 逾期**：`buildRepayForm` 逾期分支 `voteFeeAmt = overdueTotal − total`（罚息），
  使 `罚息 + Σ本息 == 本息+罚息`。仅单测覆盖，**未真实逾期实测**（库里还没到期期数）。
- **占位流水「失败→重试」语义**（P0-1 机制的洞）：`savePending` 原先"同单号存在即跳过"、
  `settlePending` 只认 PROCESSING ⇒ 银行拒单后置 FAILED，重试时 ① 不再占位（并发保护失效）
  ② 重试成功后无流水可结算（**丢一笔成功流水**）。现：savePending 遇 FAILED 重新激活为 PROCESSING；
  settlePending 允许 PROCESSING/FAILED → 终态，但不允许 SUCCESS 被降级。
