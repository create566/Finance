## 08:10 架构评审：项目是「分布式单体」，几个地方只做了微服务的一半

用户问「项目的架构设计合理吗」。实证查证后的结论：**方向对、粒度对，但有 4 处"半成品"**。

### 规模分布（决定性证据）
```
api       189 文件 / 16246 行   ← 占绝对大头（28 Controller / 56 Service / 26 Mapper）
finance-ai   76 文件 /  6088 行   ← 外挂
finance-oss   6 文件 /   542 行

```
⇒ 拆出来的三个"服务"合计 742 行，不到 api 的 5%。**不是服务拆分，是把三个小工具独立部署了。**

### 4 个"假边界"
1. **Feign 写死 URL**：`api/.../client/SMSApiSmsClient.java` 是
   `@FeignClient(value="service-sms", url="http://localhost:8120")` —— url 属性直接**绕过 Nacos 发现**。
   另一处 `finance-message/.../CoreUserInfoClient` 用 `@FeignClient("service-core")` 反向调 api
   ⇒ **双向 Feign = 循环依赖**。
2. **共享数据库**：api 连 `ww_finance`；**finance-ai 也连 `ww_finance`**
   （`ai_chat_model_binding` / `ai_model_config` / `chat_memory` / `chat_session` /
   `knowledge_base` / `knowledge_chunk` / `knowledge_doc` / `prompt_config` 共 8 张表混在主库）。
   ai 另有 Mongo `ww_finance_ai`。⇒ 微服务边界是假的，跨服务可直接改对方表。
3. **技术栈分裂（ai 不注册 Nacos 的真正原因）**：父 pom = **Spring Boot 2.3.4 / Java 8**；
   finance-ai 自己 `<spring-boot.version>3.4.8</spring-boot.version>` + Java 17，
   不继承父 pom 的 dependencyManagement。父 pom 的 Spring Cloud Alibaba 是 Boot 2.x 系，
   套不上 Boot 3.4 ⇒ **Nacos 对 ai 完全失效**，网关只能硬编码 `/ai/** → http://localhost:8081`。
4. **Nacos 只用了 1/3**：配置条目 totalCount=0，无 `spring.config.import`。只做注册中心。

### 鉴权三套实现（网关不做鉴权）
- 网关：只路由 + CORS（5173/5174），**零鉴权**
- api / oss：`finance-common` 的 `JwtAuthInterceptor`
- ai：**自己的 `AdminAuthInterceptor`**，且不依赖 finance-common/base
⇒ 包名也是三套：`com.example.demo`(api) / `com.wwfinance`(gateway·message·oss·common·base) / `com.kzip.app`(ai)
⇒ ai 明显是从别的项目搬进来的。

### 判断：合理的部分（别改回去）
- **api 保持单体是对的**：16246 行 P2P 核心业务 + 强事务（35 处 `@Transactional`），
  项目**没有 Seata 等分布式事务方案**，拆开必然掉进分布式事务坑。
- **ai 独立进程是必要且正确的**：Spring AI + Chroma + Mongo 与主业务依赖冲突风险高，且它是 Boot 3。
- **oss / message 独立合理**：外部依赖（文件存储/短信）故障隔离。
- **网关统一入口有效**：前端从记两个后端地址变成一个 8088，CORS 集中。

## 资金链路"谁在调银行"核查（用户拿了一份自述让我判对错）

用户写了一份"充值/提现/撮合/服务费"的链路自述（写报告+面试用），逐条比对代码后确认 **骨架对、4 处偏差**：

1. **最大偏差：充值/提现不是"平台调用 jar 接口"**，是**浏览器跳转 + 用户输支付密码**。
   `FormHelper.buildForm()` 返回的是 `document.form.submit()` 自动提交的 HTML（给浏览器，不是给服务端）；
   银行 `templates/userAccount/index.html` / `withdraw/index.html` 有 `payPasswd` 输入框 + "确定"按钮。
   银行 `UserAccountController` 映射：POST `/AgreeBankCharge`→`recharge()`(渲染确认页)、POST `/recharge`(真加钱)、
   POST `/CashBankManager`→确认页、POST `/withdraw`(真扣钱)。
   **六条链路里 5 条走浏览器（绑卡/充值/提现/投标/还款），只有 放款 `AgreeAccountLendProject` + 撤标 `CancelProject` 是服务端直连。**
   银行 controller 路径映射：`/userBind/BindAgreeUserV2`→`/userBind/save`；`/userInvest/AgreeUserVoteProject`→`/userInvest/invest`；`/lendReturn/AgreeUserRepayment`→`/lendReturn/returnCommit`。

2. **服务费当前一分未收**（用户自述"平台转账时收服务费转入平台银行账户"不成立）：
   `mchFee` 硬编码 `"0"`（`LendReturnServiceImpl:199`）、`LendReturn.fee` 恒 0、`Lend.service_rate` 字段**全项目零读写**（死字段）、
   银行模型只有 `UserAccount/UserBind/UserInvest/UserItemReturn/UserReturn` —— **没有平台/商户账户表**，钱无处可收。

3. **"余额不在平台数据库"要修正为"平台这表是镜像，且会降级"**：平台 `user_account` 确实存在且**真的在写**（`updateBalance` 原子 SQL）；
   `getBankBalance` 主路径是**直连银行库 SQL**（`bankJdbcTemplate` → RDS `ww_bank.user_account`），查不到才降级到平台表；
   只有 `queryBankAccount/queryBankFlow` 才走 HTTP 9090。

4. **还款是借款人自己发起**（不是平台调用、也不是到期自动）：用户端 `buildRepayForm` → 跳银行页 → 两段式（确认页 → `returnCommit` 真扣款）。

**javap 反汇编银行 jar 得到的实锤**（`ww_bank_tmp/BOOT-INF/classes`）：
- `UserAccountServiceImpl.recharge`：只 `account.amount += chargeAmt`（不存在的先 insert）—— **无银行卡对手账户、无 agent_bill_no 去重**。
- `UserAccountServiceImpl.withdraw`：只 `amount -= fetchAmt` —— 同样无转入卡账户、无去重。
- `lockAccount`：`amount -= x; freeze += x`（投标冻结）。
- `unLockAccount`：**只 `freeze -= x`，不回加 amount**（P4-51 单边记账，再确认）。
- `transferAccounts`：**只 `amount += x`**（目标账户），不扣来源账户。
- `UserInvestServiceImpl.vote`：`selectCount(agent_bill_no)` 重复即抛 `HfbException` —— **投标有幂等**；`makeLoan` 同样有。
  ⇒ **幂等分布不均：投标/放款 有，充值/提现 无**（用户重复提交银行确认页会重复入账）。
- `LendReturnServiceImpl.returnCommit`：读 `fromBindCode/totalAmt/voteFeeAmt/data`，逐户 `transferAccounts(toBindCode, transitAmt)`；
  未见 `mchFee` 字符串 ⇒ 手续费在银行侧**无收款方**（只参与 `voteFeeAmt + ΣtransitAmt == totalAmt` 等式校验）。

**教训**：分辨"平台调用银行"还是"用户浏览器调用银行"，看返回值是不是 `FormHelper.buildForm(...)` 的 HTML；是 HTML 就是跳转，是 `RequestHelper.sendFormRequest` 才是服务端直连。

## 15:12 修 P10-69：四个模块打不出 `-exec.jar`（用户打包报障 + 已实测修复）

**现象**：用户在 IDEA 对 finance-ai 执行 `package` → BUILD SUCCESS，但 target 里**只有 `finance-ai-1.0.jar`（184KB），没有 `-exec.jar`**。

**根因（关键，务必记牢）**：
- 日志里只有 `jar:3.4.1:jar (default-jar)`，**全程没有 `spring-boot:...:repackage`**。
- 原因：项目**父 pom 是自定义的 `ww_finance`（不是 `spring-boot-starter-parent`）** ⇒ 没人给
  `spring-boot-maven-plugin` 绑定 `repackage` execution。而 pom 里只写了 `<configuration><classifier>exec</classifier>`，
  **`<classifier>` 只决定产物名字，`<executions>` 才决定要不要执行 repackage** ⇒ 漏了 `<executions>` 就不打 fat jar。
- **只有 `api/pom.xml` 写了 `<executions>`**（`:157` 有注释明确写了"没用 SB parent，需显式绑 repackage 才能产出可执行 jar"、`:158-164` 是 execution），
  所以 api 一直能出 `-exec.jar`。
- `finance-gateway` / `finance-message` / `finance-oss` / `finance-ai` **四个模块都只有 `<classifier>`，漏 `<executions>`**。

**修复（已改 4 个 pom）**：给四个模块的 `spring-boot-maven-plugin` 各补上：
```xml
<executions><execution><goals><goal>repackage</goal></goals></execution></executions>
```
（gateway :43-47 / message :57-61 / oss :76-80 / ai :配置块后缀）

**实测验证**：finance-ai 重新 `package -DskipTests` → 日志出现
`Attaching repackaged archive ...\finance-ai-1.0-exec.jar with classifier exec` + `goal=repackage`，
target 里 **`finance-ai-1.0-exec.jar` 66.5MB（fat）+ `finance-ai-1.0.jar` 184KB（thin）** 同时产出 ✅。

**教训（可复用）**：**不用 `spring-boot-starter-parent` 的项目，`spring-boot-maven-plugin` 必须显式写 `<executions><goal>repackage</goal></executions>`**，
光配 `<classifier>` 是无效的。判断是否绑上：看 `mvn package` 日志里有没有 `repackage` 这行。

- 命令：`start`（顺序 + 逐个等端口就绪）/ `stop`（逆序）/ `restart`（逆序停 + 顺序起）/ `status [svc]` / `start|stop|restart <svc>`（单服务，**不走依赖链**）/ `logs <svc>`（tail -f）/ `help`。
- 机制：pid 文件 `run/<svc>.pid`（兜底 `pgrep -f <jar>`）、日志 `logs/<svc>.log`（追加+带时间戳分隔）、
  优雅停止（TERM → 等 30s → KILL -9）、启动前检查 jar 是否存在 + 端口是否已被占、JDK 按服务选（`JAVA8_HOME`/`JAVA17_HOME` + 常见路径探测）。
- ⚠️ **踩坑：MSYS2(Git Bash) 下 `/dev/tcp` 不可靠** —— 用它探端口会**假阳性**（未监听的端口也返回成功），
  导致 `status` 全显示 yes。**改用 `ss -ltn` → `netstat -ltn` → `netstat -an` 三级取监听表 + awk 精确匹配 `:PORT$`** ⇒ 本地与 Linux 都准。
- `status` 三态：`UP`（脚本启动，有 pid）/ `EXT`（端口在监听但无本脚本 pid ⇒ 多半是 IDEA 启的）/ `DOWN`。
- 交付提醒：上传后需 `chmod +x manage.sh`（Windows 下无法置执行位）；也可 `bash manage.sh start`。
