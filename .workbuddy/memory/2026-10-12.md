## 09:1x 🔴 定位并修复：AI 模块「跨机（frp/公网）删除文件失败、本机 localhost 正常」

**现象**：前端经 frp 暴露到云服务器（`http://120.26.132.5` 用户端 :80 / 管理端 :81），后端跑在本机。
别人电脑打开前端后 **AI 知识库删不了文件**，本机 localhost 正常；api/oss 等模块也正常。

**根因**：`finance-ai/src/main/java/com/kzip/app/config/CorsConfig.java`（`WebMvcConfigurer`）自带
**独立**的 CORS 白名单 `ALLOWED_ORIGINS`，只有 `localhost/127.0.0.1` 的 5173/5174/8081，**不含公网 IP**。
三个关键点：
1. **同源请求也带 `Origin`**：浏览器对**非 GET** 请求一律附带 Origin；Spring 的
   `CorsUtils.isCorsRequest()` **只判"有没有 Origin 头"** ⇒ 走 CORS 白名单校验 ⇒
   **只有写操作(DELETE/POST/PUT)挂，读取(GET)正常**（同源 GET 不带 Origin）。
2. 不命中白名单 ⇒ `rejectRequest()` ⇒ **403 + 纯文本 `Invalid CORS request`**（非 JSON、非 401）。
3. **网关救不了**：网关 `CorsWebFilter` 白名单**已含**公网 IP，但对非预检请求只是"加头放行"，
   不阻止下游再校验 ⇒ 经 8088 + 公网 Origin 实测仍 403。
4. **全项目只有 finance-ai 有这道自有 CORS**（api `MyWebConfig` / finance-base `WebMvcConfig` /
   oss 两个 config 都无 CORS）⇒ 这才是"为什么只有 AI 挂"。与 Nacos 无关（AI 不注册，网关静态 URI 直连 8081）。

**实测证据（`curl --noproxy "*"` 直连 8081）**：Origin=公网:81 → DELETE/GET/**预检 OPTIONS** 全 **403**；
Origin=localhost:5173 或无 Origin → **401**（CORS 放行、仅缺登录）；经 8088 + 公网 Origin → 403。

**修复**：`ALLOWED_ORIGINS` 追加 `http://120.26.132.5`、`http://120.26.132.5:81`（与网关白名单对齐）。
**验证**：`-pl finance-ai -am package`（JDK17 + plexus 启动器）SUCCESS → 新 `finance-ai-1.0-exec.jar`；
`grep -a` 核验 class 常量池含两条公网来源；起**隔离实例 8082** → 公网 Origin 的 DELETE/GET 返 401、
预检 OPTIONS 返 200 + `ACAO: http://120.26.132.5:81`，而旧 8081 仍 403 ⇒ **修复确认**；测完杀 8082、清临时日志。

**生效方式**：源码与 jar 已就绪，但运行中的 8081 是旧字节码 ⇒ 需停 ai → 覆盖
`D:\桌面\实训jar包\finance-ai-1.0-exec.jar` → 重启（Windows 会锁运行中的 jar，必须先停）。

⚠️ **伴生隐患（未处理）**：网关与 AI **都**写 ACAO ⇒ 响应有**重复头**；同源部署下浏览器不校验故无害，
**真跨源（前端与 API 不同 host/port）会因 "contains multiple values" 直接失败**。根治需二者只留一处 CORS。

⚠️ 小坑：本机**没有 `strings` 命令**（PortableGit 不全），查 jar 内 class 的字符串常量用 `grep -a`。

## 21:0X 用户报 "Port 8081 already in use" —— 实为重复启动，AI 早已跑起来

**用户贴的报错**：`Web server failed to start. Port 8081 was already in use.`（退出码 1）

**诊断**：
- `netstat -ano | grep :8081` → **PID 33644 (java.exe) 正在 LISTENING**。
- `curl http://127.0.0.1:8081/ai/health/status` → **HTTP 200**，返回：
  ```json
  {"service":"ai-module","version":"1.0.0","status":"DEGRADED",
   "components":{"vectorStore":{"status":"UP","responseTime":"95ms"},
                 "chromaDB":{"status":"DOWN","httpStatus":410}}}
  ```
⇒ **AI 子模块已成功运行**，用户再次点启动才撞端口。**不是故障，是重复启动。**

**结论 / 给用户的说法**：
- 无需再启动，8081 上已有健康的 AI 实例（可直接被 api/gateway 调用）。
- 若要重启：先停掉 PID 33644 的实例，再启动；或直接沿用现有实例。
- `chromaDB: DOWN (410)` 是**健康检查探测方式问题**（用 GET 探已弃用的心跳端点），
  **真正的 `vectorStore` 是 UP（95ms）**，不影响 RAG。

**沉淀**：报 `Port XXXX already in use` 时，**先 `netstat` 找占用者 + `curl` 探它是不是同类服务**，
再决定"杀掉重启"还是"直接复用" —— 别条件反射式杀进程。
