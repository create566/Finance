# ww_finance 接口 QPS 压测报告

- **被测服务**：`http://127.0.0.1:8990`（api 模块，Spring Boot）
- **压测工具**：Apache JMeter 5.6.3（无界面模式 `-n`），JDK 17
- **压测脚本**：`ww_finance_benchmark.jmx`（原始文件位于桌面根目录）
- **测试时间**：2026-10-09 10:43 ~ 11:00
- **运行环境**：本机 Windows 11，16 逻辑核，JMeter 与 api 服务同机运行（**压测机与被测机未隔离，结果偏保守**）

---

## 一、结论摘要

| 场景 | 并发 | QPS | 平均延迟 | P95 | 错误率 |
|---|---|---|---|---|---|
| 混合 9 接口（原用例设计） | 40 | **637 /s**（稳态）<br>600.9 /s（全程） | 57 ms | 475 ms | **0.00%** |
| 混合 9 接口 | 20 | 597 /s | 33 ms | 215 ms | 0%（见备注①） |
| 混合 9 接口 | 80 | 564 /s（**开始下降**） | 140 ms | 1004 ms | 0.00% |
| 纯读 7 接口（剔除 05、09） | 40 | **1296 /s** | 26 ms | — | — |
| 纯读 7 接口（剔除 05、09） | 80 | **1462 /s** | 47 ms | — | — |

**核心结论：**

1. **当前配置下混合读场景的吞吐天花板约为 600~640 QPS**（并发 40 时达到，并发升到 80 反而降至 564 QPS 且延迟翻倍，已过拐点）。
2. **瓶颈是 `05 账户信息` 接口**：它依赖银行模拟服务（:9090），平均延迟 203 ms @20 并发 → 457 ms @40 → 1014 ms @80，把整个混合场景的吞吐拉低了一半。剔除该接口后，纯读吞吐可达 **1300~1460 QPS**。
3. 除 `05 账户信息` 外，其余读接口延迟均在 **8~40 ms** 量级，P95 基本在 50 ms 内，服务本身处理能力良好。

## 二、发现的两个用例缺陷

### 缺陷 1：采样器 `09 管理端标的列表` 继承借款人身份 → 100% 403

- **现象**：原始用例运行时，09 接口 **100% 返回 403**，占全部请求的 11%，导致整体错误率 11%。
- **根因**：JMeter 的 HeaderManager 是**合并**语义——线程组级设置了 `Authorization: ${__P(userToken)}`（借款人），采样器 09 只**新增**了 `token` 头，没有**覆盖** `Authorization`。两个头同时发出，服务端 `JwtAuthInterceptor` 优先按 `Authorization` 判定身份，于是以**借款人**身份访问 `/admin/**` → 403。
- **证据**（对照实验）：

  | 请求头组合 | 响应 |
  |---|---|
  | `token: <adminToken>` | 200 |
  | `Authorization: <adminToken>` | 200 |
  | `token: <adminToken>` + `Authorization: <adminToken>` | 200 |
  | `token: <adminToken>` + `Authorization: <userToken>` | **403** |

- **修复**：给采样器 09 的 HeaderManager 补上 `Authorization: ${__P(adminToken)}`（与采样器 08 的写法保持一致）。修复文件见 `ww_finance_benchmark.fixed.jmx`。

### 缺陷 2：环境侧干扰——单会话机制导致 token 被"顶号"失效

- **现象**：压测进行到中段，某个接口**突然从 200 全部变 401**（如修复版 09：前 19.6 秒 940 次成功，之后 6712 次全部 401）。
- **根因**：服务端 `JwtAuthInterceptor` 采用**隐式单会话**设计——Redis 键 `login:token:admin:<id>` 只保存一个 token，且校验要求**完全相等**（`JwtAuthInterceptor.java:127`）。**任何其他客户端用同一账号再登录一次，压测持有的 token 立即失效。**
- **证据**（api 访问日志 `logs/access/api-access.2026-10-09.log`）：

  ```
  10:45:32.845  127.0.0.1        POST /admin/core/login  200   ← JMeter setUp 取得 adminToken
  10:45:52.442  192.168.112.1    GET  /admin/core/logout  401   ← 外部客户端（非压测机）
  10:45:53.358  192.168.112.1    POST /admin/core/login   200   ← 抢登 admin → 顶掉压测 token
  ```

  另：原始用例最后一秒 `01 标的列表` 的 1795 次 401，对应 `10:45:05.774` 另一次完整 setUp 登录（覆盖了借款人 token）。

- **说明**：这是**测试环境干扰**，不是服务缺陷，也不是压测脚本缺陷。token 本身有效期 7 天且每次请求续期（已解码 JWT 确认），不存在过期问题。

## 三、并发梯度明细（混合 9 接口，45s/轮）

| 并发 | QPS(稳态) | 平均延迟 | P50 | P90 | P95 | P99 | 错误率 | `05 账户信息` 平均延迟 |
|---|---|---|---|---|---|---|---|---|
| 20 | 597 | 33 ms | 9 | 171 | 215 | 243 | 0%① | 203 ms |
| 40 | **637** | 63 ms | 9 | 357 | 476 | 514 | 0.00% | 457 ms |
| 80 | 564 | 140 ms | 20 | 672 | 1004 | 1420 | 0.00% | **1014 ms** |

① 20 并发轮的 7.92% 错误全部来自采样器 08，被测时段内被外部客户端抢登投资人账号所致，非服务问题。

## 四、建议

1. **压测专用账号**：为压测单独准备管理员/借款人/投资人账号，避免与前端、Postman、手工调试共用——单会话机制下共用账号必然互相顶号。
2. **压测窗口隔离**：压测期间不要在浏览器/Postman 上操作同一账号。
3. **关注 `05 账户信息`**：它是吞吐瓶颈（依赖 :9090 银行模拟服务）。若要提升整体 QPS，可考虑对该接口的银行调用做缓存或异步化，或单独对它做容量测试。
4. **压测机与被测机分离**：当前 JMeter 与 api 同机，CPU 相互竞争，实测数值偏保守（真实上限应高于 640 QPS）。
5. 若继续提高并发，建议同时监控 api 服务的 JVM GC、数据库连接池与银行模拟服务的响应时间，以定位 80 并发下延迟陡增的原因。
