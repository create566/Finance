接口现象说明
POST /api/core/contract/auth/prepare缺陷 调用者不是「该标的的借款人」时，唯一键 uk_biz 冲突直接抛库异常， 返回 code=500 且 msg 里带出 SQLIntegrityConstraintViolationException 与 Mapper 类名 —— 敏感信息泄露。 期望应为 403 您不是该合同的签署方。根因：findOne() 用「调用者 userId」当 party_a_id 查重， 而 fillParties() 把 LOAN/PAYMENT 甲方写成「借款人 id」，两者不一致 ⇒ 查不到 → 插入 → 撞唯一键。建议修复。
GET .../dict/listByCode缺陷 参数名必须是 dictCode；缺失或写错时返回 500 系统内部错误，而非 400 参数校验提示。
POST /admin/core/dict/category缺陷 取的是 body 里的 dictCode（不是 code）；传 code 不会报错，会静默建出 dict_code=NULL 的脏分类（本轮实测复现）。建议加参数校验。
PUT /admin/core/dict/update缺陷 撞唯一键 uk_parent_id_value(parent_id,value) 时返回 500 系统内部错误， msg 无任何有效信息。同类问题：多个写接口把 DB 约束冲突直接冒泡成通用 500。
PUT .../contract/template/{id}/status缺陷 status 是 query 参数（@RequestParam）；放 body 里会 500「系统内部错误」。 且该方法的 catch 只捕获 ResourceNotFoundException，其它异常一律冒泡成通用 500。
GET /api/core/chat/message/list正常 查询非本人会话返回 403 无权访问他人会话 —— 越权修复后的正确行为，不是缺陷。
充值 / 提现 / 还款 / 投标HTML 业务成功时返回银行 HTML 表单（跳转存管银行确认页），不是 JSON； 业务失败却是 HTTP 200 + JSON {"code":400}，前端靠 parseErrorEnvelope() 区分。

本轮（含写操作）说明：104 个接口 + 1 个补充回查 = 105 条用例全部真实执行（不再跳过写操作）。 未通过的 15 条全部是前置条件/数据/环境不满足，不是接口缺陷，典型包括： 标的 111 已是「已下架」不能重复上架/下架；库里没有「待审核」的借款申请与「认证中」的实名记录； 实名认证与借款申请缺身份证影像等必填材料；投资人未签《出借协议》、借款人未签《资金存管协议》； 两个测试账号银行可用余额为 0（提现/还款报「可用余额不足」）； 存管银行 9090 未启动 → 放款返回「银行无应答」。 建议按此顺序补前置条件后再跑：签协议 → 充值 → 投标/还款。

说明：充值/提现/还款/投标/放款成功时返回的是【银行 HTML 表单】而非 JSON， 本报告对这类响应按 HTML 摘要展示。标「跳过」的是写操作，为避免污染业务数据未执行。
