## 0. 一句话结论

**规格描述的三类合同里，只有第 1 类（借款合同）有对应实现，但它的"乙方（投资人）"是空的；第 2、3 类（居间服务协议、资金存管协议）在系统里完全不存在。**
"借款合同"在本系统中实际是**借款人单方签署的、面向不特定投资人的格式合同**，真正的"借款人 ↔ 投资人"双边关系落在**《出借协议》**上，且是**按投资笔数每人一份**、在**投标下单前**签署——而不是规格说的"满标后生成一份双方合同"。

## 1. 三类核心合同逐条对照

| 规格 | 实际实现 | 判定 |
| --- | --- | --- |
| **① 借款电子合同**<br>主体：借款人（甲方）↔ 投资人（乙方）<br>平台：居间方（见证人）<br>时机：**满标成功后自动生成** | **存在但主体错位**：`contract_type='LOAN'`，标题"借款合同"。`party_a_id` = **借款人**，`party_b_id` = **NULL**（实测 6/6 全空）。正文写"甲方（出借人）：旺旺金融平台投资人 / 乙方（借款人）：${borrowerName}"。**建标时即预生成，上架募资前必须签**（此时还没有任何投资人） | ⚠️ **部分符合，主体错位** |
| **② 居间服务协议**<br>平台↔借款人、平台↔投资人<br>作用：约定撮合服务、明确服务费规则 | **完全不存在**。全库无任何 `%agree%` / `%service%` / `%deposit%` 表；唯一相关字段是 `lend.service_rate`（"平台服务费率"），且**全项目零读写**（死字段）。仅在《出借协议》正文里有一句"中介服务平台：旺旺金融（仅提供信息中介服务，不承担代偿责任）" | ❌ **缺失** |
| **③ 资金存管协议**<br>用户 ↔ 模拟银行<br>时机：注册、绑卡时签署 | **完全不存在**。平台侧没有任何存管协议记录；绑卡只落一条 `user_bind` 再同步到银行库（`BankBindController.bindDirect`）。用户端绑卡走 `POST /api/user/bindDirect` **直连落库，根本不经银行页面** | ❌ **缺失** |

## 2. 三个根本性错位（这是核心问题）

### 错位 A：《借款合同》里"乙方（投资人）"是空的 —— 实测 6/6 全 NULL

`ContractServiceImpl.fillParties()` 的分支逻辑（`ContractServiceImpl.java:120-132`）：

```java
/** 甲方/乙方按合同类型归属：出借协议甲方=投资人、乙方=借款人；其余甲方=借款人 */
private void fillParties(Contract c, ContractTypeEnum type, Lend lend, Long partyId) {
    Long borrowerId = lend.getUserId();
    if (type == ContractTypeEnum.INVEST) {
        c.setPartyAId(partyId);          // 甲方 = 投资人
        c.setPartyBId(borrowerId);       // 乙方 = 借款人
    } else {
        c.setPartyAId(borrowerId);       // LOAN / PAYMENT：只设甲方 = 借款人
        // ← party_b 不赋值，保持 NULL
    }
}
```

实测库数据（`contract` 表，`is_deleted=0`）：

| contract_type | 份数 | `party_b_id IS NULL` | 待签 | 已签 | 已作废 |
| --- | --- | --- | --- | --- | --- |
| LOAN 借款合同 | 6 | **6** | 2 | 1 | 3 |
| PAYMENT 放款确认书 | 4 | **4** | 2 | 2 | 0 |
| INVEST 出借协议 | 10 | 0 | 6 | 4 | 0 |

样本：

```
id=12  LOAN     biz_id=6    party_a=33/张三   party_b=NULL/NULL   10000.00  已签
id=13  LOAN     biz_id=10   party_a=33/张三   party_b=NULL/NULL   10000.00  待签
id=14  PAYMENT  biz_id=10   party_a=33/张三   party_b=NULL/NULL   10000.00  已签
```

**后果**：合同可见性由"甲方或乙方 == 当前用户"决定（`ContractServiceImpl.java:333`）。乙方为空 ⇒ **投资人永远看不到《借款合同》**，`idx_party_b` 索引成为死索引。

### 错位 B：模板正文的甲乙方，与数据库字段指向相反的人

`contract_template` 里 TPL_LOAN 启用版（v2，实测 442 字符）正文原文：

```
借款合同
合同编号：${contractNo}

甲方（出借人）：旺旺金融平台投资人
乙方（借款人）：${borrowerName}
身份证号：${borrowerIdCard}

一、借款金额：人民币 ${amount} 元
二、借款期限：${period} 期
三、年化利率：${lendYearRate}%
四、还款方式：按借款申请约定执行
五、借款用途：${purpose}

乙方承诺：所提供资料真实有效，按期还本付息；逾期按平台规则计收罚息并上报征信。
本合同自乙方手写签署之日起生效...

签署人（乙方）：____________    签署日期：${signDate}

六、放款确认与逾期处理：...
```

正文说 **甲方 = 出借人（投资人）**，而库里 `party_a_id = 33（张三，借款人）`。**同一份合同，正文和字段把"甲方"指给了相反的人**。`sql/contract_overdue_clause.sql:50-52` 追加的条款同样写"甲方（出借人）有权终止本次借贷"——沿用了这个错误口径。

同时注意：正文里**只有"签署人（乙方）"一个签名位，甲方没有签名位** —— 这与"只有借款人单方签"的事实一致，也与"双方签订"的规格直接冲突。

### 错位 C：数据模型从设计上就容纳不了"双边共同一份合同"

`sql/contract.sql` 的唯一键：

```sql
UNIQUE KEY `uk_biz` (`biz_type`, `biz_id`, `contract_type`, `party_a_id`, `is_deleted`, `amount`)
-- 注释原文：出借协议按投资人 + 金额区分：同一标的下每个投资人各一份
```

唯一键里含 **`party_a_id` + `amount`** ⇒ 数据模型把"一份合同"定义为 **"某个甲方 + 某个金额"**。
- 单标的多投资人的事实，实测：

| lend_id | LOAN 份数 | INVEST 份数 | PAYMENT 份数 |
| --- | --- | --- | --- |
| 10 | **1** | **2** | 1 |
| 101 | 1 | 1 | 1 |
| 103 | 0 | 2 | 0 |

标的 10 有 2 个投资人，却只有 **1 份**《借款合同》，且该合同乙方为空、甲方字段指向借款人。
⇒ **"1 份借款合同 = 1 个借款人 + N 个不特定投资人"**，与规格"借款人 ↔ 投资人 双方共同一份"是**两种不同的法律结构**，不是细节差异。

## 3. 生成与签署时机对照

| 环节 | 规格 | 实际 | 证据 |
| --- | --- | --- | --- |
| 借款合同生成 | 满标成功后自动生成 | **建标（待发布）时预生成** | `LendServiceImpl.java:91-94` `createLend()` |
| 借款合同签署 | 满标时双方电子签章 | **上架募资前**借款人必须签（关口一），手写签名 | `LendServiceImpl.java:276-277` `publish()` → `assertSigned(...)` |
| 满标时 | 生成合同 + 双方签章 + 资金划转 | **只翻状态**：`status=COMPLETED` + 写 `complete_time` + 投资记录置 2 + 清缓存 + 发催签站内信。**不生成任何合同、不签章、不划款** | `LendItemServiceImpl.handleInvestNotify` 满标分支 |
| 资金划转 | 满标时投资人账户 → 借款人账户 | **放款时**，且由**管理端人工触发**的服务端同步调用（`makeLoanSync`），非自动 | `AdminLendController.makeLoan` |
| 投资人侧合同 | 借款合同（乙方） | **《出借协议》**，按投资笔数每人一份，**投标下单前**必须签（硬闸门） | `LendItemServiceImpl.java:159` `assertSigned(...INVEST...)` |
| 放款确认 | 无此环节 | **额外多出**《放款确认书》，借款人放款前必须签 | `ContractTypeEnum.PAYMENT` |

`ContractTypeEnum` 的注释本身就写着与规格不符的定义：

```java
/** 借款合同：借款人与平台签署，标的发布募资前必须签 */
LOAN("LOAN", "借款合同", "TPL_LOAN"),
```

**"借款人与平台签署"** —— 这既不是规格的"借款人↔投资人"，也解释了为何乙方为空。

## 6. 面试/答辩口径建议

按上面的证据，**不能**照规格的说法讲，会被追问到崩。建议这样表述：

1. **"双边借款关系落在《出借协议》上，不是《借款合同》"** —— 《出借协议》甲方=投资人、乙方=借款人，双方实名（姓名+身份证脱敏）、双方签名位齐全，是**唯一真正的双边借贷合同**；《借款合同》是**借款人单方签署、面向不特定投资人的格式合同**（`party_b_id` 留空是设计结果，不是数据缺陷）。
2. **"我实现的是'一标多投资人各一份出借协议'模型"** —— 由 `uk_biz(biz_type,biz_id,contract_type,party_a_id,amount)` 唯一键保证；这在多对一撮合场景下比"双方共同一份"更易落地（每个投资人的出借金额、签署时间都不同）。
3. **必须主动承认的两个缺口**：① 居间服务协议与资金存管协议尚未建模，服务费无合同依据（与"银行返点模式、暂不收服务费"的决策一致，但**"无依据"和"暂不收"要分清**）；② 罚息当前按"归平台"实现，与"归投资人"的行业口径不一致，属**待定的产品口径**，不是已实现能力。
4. **千万别说的**：不要说"满标后自动生成并双方签章"（实际不生成、不自动签）、不要说"注册时签了存管协议"（实际没有）、不要说"合同可下载"（实际不能）。
