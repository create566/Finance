# 合同签署 + 标的推荐 —— 方案设计

> 项目：旺旺金融信贷系统（ww_finance 实训版）
> 模块：`api`（finance-api，核心业务服务，8110）
> 前端：`ww/ww_finance_user`（用户端）、`ww/ww_finance_admin`（管理端）
> 文档版本：v1.0 · 2026-09-30

---

## 0. 需求原文与拆解

> "该项目生成标业务中，必要时需要手动签名，保证安全。借款合同，投资合同之类，推荐标给投资人。"

拆成两件事：

| # | 需求 | 落地形态 |
|---|------|---------|
| **需求 A** | 生成标业务中，**必要时需要手动签名**保证安全 —— 借款合同、投资合同 | 新增「电子合同签署」模块：合同模板 → 合同实例 → 手写签名 → 存证；并在**关键资金动作前做强校验**（未签不放行） |
| **需求 B** | **推荐标给投资人** | 新增标的推荐：规则打分版（必做）+ Item-CF 协同过滤（进阶），用户端首页/详情页展示 |

**"必要时"的准确含义**：不是所有环节都要签，只在**产生法律/资金责任**的关口签。本方案定为 3 个签署关口（见 §2.2）。

## 1. 现状核查（已逐文件确认）

### 1.1 标的链路已有什么

| 环节 | 代码位置 | 现状 |
|------|---------|------|
| 借款申请审批 | `BorrowInfoServiceImpl.approveBorrowInfo()` | 审批通过 → **自动建标** `lendService.createLend()`；已有"一个申请只建一个标"的防重 |
| 手工建标 | `AdminLendController.create()` `POST /admin/core/loan/project` | 直接落 `status=1 募资中`（后台测试用） |
| 标的发布 | `LendServiceImpl.publish()` `PUT /admin/core/loan/project/{id}/publish` | 待发布(0) → 募资中(1)；**已有风控校验**：金额 100~100万、年化 5%~14.6%、期数 1~36、募集 7 天 |
| 标的下架 | `LendServiceImpl.offline()` | 待发布/募资中 → 已下架(4) |
| 满标放款 | `LendReturnServiceImpl.buildMakeLoanForm()` `PUT /{id}/makeLoan` | 生成银行放款表单，入账靠银行异步回调 |
| 投资下单 | `LendItemServiceImpl.buildInvestForm()` `POST /api/core/lend/invest/{lendId}` | 校验「投资人身份 → 绑卡 → 标的状态 → 起投金额 → 余额」，**已有 Redis 分布式锁防超投**；通过后返回银行支付表单 HTML |

**标的状态机**（`LendStatusEnum`）：
`0 待发布 → 1 募资中 → 2 已满标待放款 → 5 还款中 → 6 已完结`，旁支 `3 已逾期 / 4 已下架 / 7 已流标`。

### 1.2 缺什么

- ❌ **没有任何合同/签约相关代码**（全库 grep `合同|contract|signature|签章` 只命中 `TokenUtil` 的 JWT 签名）
- ❌ **数据库中无合同表**（31 张表里只有 `investor`/`investor_attach` 是投资人实名认证）
- ❌ **没有推荐接口**。`ww_finance_API接口文档.md` 里写的 `GET /api/core/lend/auth/recommend`（Item-CF）**在本工程未实现**，`LendController` 只有 list/detail/invest/investments/myInvestments

### 1.3 可复用的既有能力

| 能力 | 复用点 |
|------|-------|
| 统一返回 | `PccAjaxResult`（code/msg/data） |
| 异常 | `ResourceNotFoundException(code, msg)` → 全局处理器转标准返回 |
| 登录态 | `LoginUserContext.getUserid()`（拦截器已解析 JWT） |
| 文件存储 | `OssFileController` `POST /api/oss/file/upload`（本地 `D:/uploads`，≤50MB） |

| 逻辑删除/自动填充 | `@TableLogic`、`@TableField(fill=...)` + `MetaObjectHandler` |

## 2. 需求 A：电子合同签署模块

### 2.1 签名形式选型

| 方案 | 实现成本 | 防抵赖强度 | 适用性 |
|------|---------|-----------|--------|
| **A. Canvas 手写签名 → PNG 存证**（✅ 推荐） | 低（纯前端组件 + 一次上传） | 中：签名图 + IP + UA + 时间 + 内容哈希 | 实训项目最佳。不接真实资金通道（大纲明确禁止），但完整覆盖"签名验签/防抵赖/幂等"教学目标 |
| B. 姓名输入 + 短信验证码确认 | 最低 | 弱：无生物特征 | 可作为 A 的降级兜底（手写板不可用时） |
| C. 上传已签纸质合同扫描件 | 低 | 中 | 适合线下场景，作为附件补充 |
| D. 第三方 CA 电子签章（法大大/e签宝） | 高（需企业资质+付费） | 强 | ❌ 不适用，实训项目不接外部通道 |

**结论：采用 A 为主 + B 为降级**。签名图 + 内容 SHA-256 快照 + 四要素存证，已足够"保证安全"。

### 2.2 签署关口（"必要时"的界定）

| # | 合同类型 | 签署方 | 卡在哪个动作前 | 未签的后果 |
|---|---------|-------|--------------|-----------|
| 1 | **《借款合同》** | 借款人（Party A） | `LendServiceImpl.publish()` —— 标的上架募资前 | 标的状态停在"待发布"，无法募资 |
| 2 | **《出借协议 / 投资合同》** | 投资人（Party B） | `LendItemServiceImpl.buildInvestForm()` —— 下单生成支付表单前 | 返回"请先签署《出借协议》"，前端引导跳签名页 |
| 3 | **《放款确认书》** | 借款人 | `LendReturnServiceImpl.buildMakeLoanForm()` —— 满标放款前 | 无法放款 |

> **设计要点**：合同在**标的一生成时（`createLend`）就预生成**，状态 `0 待签署`。
> 借款人进入"我的合同"即可签；到 `publish` 时只做**校验**，而不是"到 publish 才生成"——
> 这样用户有充足时间签，也不会把生成逻辑塞进发布事务里。

### 2.3 数据模型（新增 3 张表）

```sql
-- ① 合同模板（后台可维护，正文用 ${} 占位符）
CREATE TABLE `contract_template` (
  `id`            BIGINT       NOT NULL AUTO_INCREMENT,
  `template_no`   VARCHAR(64)  NOT NULL COMMENT '模板编号',
  `contract_type` VARCHAR(32)  NOT NULL COMMENT 'LOAN借款合同 / INVEST出借协议 / PAYMENT放款确认书',
  `title`         VARCHAR(128) NOT NULL COMMENT '合同标题',
  `content_tpl`   TEXT         NOT NULL COMMENT '正文模板，变量用 ${变量名}',
  `variables`     VARCHAR(512)          COMMENT '变量清单(逗号分隔)，供前端提示',
  `version`       INT          NOT NULL DEFAULT 1 COMMENT '版本号，签后不随模板变更',
  `status`        TINYINT      NOT NULL DEFAULT 1 COMMENT '1启用 0停用',
  `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `is_deleted`    TINYINT      NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_template_no_ver` (`template_no`, `version`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='合同模板';

-- ② 合同实例（一份合同 = 一条；biz 关联标的/借款申请/投资记录）
CREATE TABLE `contract` (
  `id`                BIGINT       NOT NULL AUTO_INCREMENT,
  `contract_no`       VARCHAR(64)  NOT NULL COMMENT '合同编号，唯一',
  `contract_type`     VARCHAR(32)  NOT NULL COMMENT '同模板 contract_type',
  `biz_type`          VARCHAR(32)  NOT NULL COMMENT 'LEND / BORROW_INFO / LEND_ITEM',
  `biz_id`            BIGINT       NOT NULL COMMENT '业务主键',
  `template_id`       BIGINT       NOT NULL,
  `template_version`  INT          NOT NULL COMMENT '签署时的模板版本（追溯用）',
  `party_a_id`        BIGINT       NOT NULL COMMENT '甲方 userId（出借方=投资人 / 借款方=借款人，按类型语义定）',
  `party_a_name`      VARCHAR(64)  NOT NULL,
  `party_b_id`        BIGINT                COMMENT '乙方 userId（部分合同单方签署，可为空）',
  `party_b_name`      VARCHAR(64),
  `amount`            DECIMAL(16,2)         COMMENT '合同金额',
  `lend_year_rate`    DECIMAL(6,2)          COMMENT '年化利率%',
  `period`            INT                   COMMENT '期数',
  `start_date`        DATE,
  `end_date`          DATE,
  `content_snapshot`  MEDIUMTEXT   NOT NULL COMMENT '正文快照：变量渲染后的全文，签署后冻结',
  `content_hash`      CHAR(64)     NOT NULL COMMENT '正文 SHA-256，防事后篡改',
  `status`            TINYINT      NOT NULL DEFAULT 0 COMMENT '0待签署 1已签署 2已作废',
  `sign_count`        INT          NOT NULL DEFAULT 0 COMMENT '已签署方数量',
  `sign_deadline`     DATETIME              COMMENT '签署截止时间（可选，超时自动作废）',
  `revoke_reason`     VARCHAR(255)          COMMENT '作废原因',
  `create_time`       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  `is_deleted`        TINYINT      NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_contract_no` (`contract_no`),
  -- 幂等关键：同一业务的同一类合同只能有一份（防重复生成）
  UNIQUE KEY `uk_biz_type` (`biz_type`, `biz_id`, `contract_type`, `is_deleted`),
  KEY `idx_party_a` (`party_a_id`, `status`),
  KEY `idx_party_b` (`party_b_id`, `status`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='合同实例';

-- ③ 签署存证（一次签名 = 一条，含手写签名图与防抵赖四要素）
CREATE TABLE `contract_sign_record` (
  `id`            BIGINT       NOT NULL AUTO_INCREMENT,
  `contract_id`   BIGINT       NOT NULL,
  `signer_id`     BIGINT       NOT NULL COMMENT '签署人 userId',
  `signer_role`   VARCHAR(16)  NOT NULL COMMENT 'PARTY_A / PARTY_B',
  `signer_name`   VARCHAR(64)  NOT NULL,
  `signer_id_card` VARCHAR(32)          COMMENT '身份证号（投资人/借款人实名认证取值）',
  `sign_img_url`  VARCHAR(255) NOT NULL COMMENT '手写签名图 URL（OSS/本地 uploads）',
  `content_hash`  CHAR(64)     NOT NULL COMMENT '签署时再次校验的正文哈希，与 contract 必须一致',
  `sign_ip`       VARCHAR(64),
  `user_agent`    VARCHAR(255),
  `sign_time`     DATETIME     NOT NULL,
  `create_time`   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  -- 幂等关键：同一人同一合同只能签一次
  UNIQUE KEY `uk_contract_signer` (`contract_id`, `signer_id`),
  KEY `idx_signer` (`signer_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='合同签署存证';
```

> **为什么 `content_snapshot` + `content_hash` 是安全核心**：
> 合同正文一旦签署就**冻结**。后续管理员改了模板，历史合同不受影响（靠 `template_version` 追溯）；
> 任何试图改库改正文的行为，都会让 `content_hash` 对不上，可被一眼查出。

### 2.5 核心流程

```
① 标的生成时预生成借款合同
   BorrowInfoServiceImpl.approveBorrowInfo()  →  createLend()
                                                    └→ contractService.createContract(BORROW, lendId, 借款人)
   AdminLendController.create()                →  └→ 同样预生成

② 借款人在用户端签署
   我的合同列表 → 详情（读 content_snapshot）→ 手写签名 → 上传签名图 → 落存证 → status=1

③ 标的发布前强校验（拦截点）
   LendServiceImpl.publish()
        └→ contractService.assertSigned(LEND, lendId, LOAN)
             未签 → throw ResourceNotFoundException(500, "标的《借款合同》尚未签署，无法发布募资")

④ 投资人下单前强校验（拦截点）
   LendItemServiceImpl.buildInvestForm() 第1步之后
        └→ 已签：复用历史合同，直接放行
           未签：throw ResourceNotFoundException(500, "请先签署《出借协议》")  ← 前端捕获后引导签名

⑤ 满标放款前强校验（拦截点）
   LendReturnServiceImpl.buildMakeLoanForm()
        └→ contractService.assertSigned(LEND, lendId, PAYMENT)
```

### 2.6 安全设计对照表（回应"保证安全"）

| 风险 | 对策 | 落点 |
|------|------|------|
| 重复生成合同 | 唯一索引 `uk_biz_type(biz_type, biz_id, contract_type, is_deleted)` | 建表 |
| 重复签名 | 唯一索引 `uk_contract_signer(contract_id, signer_id)` + 签署前先查 | 建表 + Service |
| 并发签名/发布 | Redis 分布式锁（复用 `LendItemServiceImpl.tryLock` 模式） | Service |
| 事后篡改正文 | `content_hash` SHA-256，签署时二次校验 | Service |
| 模板变更影响历史合同 | `content_snapshot` 冻结 + `template_version` 追溯 | 表设计 |
| 冒名签署 | 签署人必须 = 登录用户，且必须是该合同的 party_a/party_b | Service |
| 非本人标的 | 沿用既有"不能投资自己的标的"校验 | 已有 |
| 签名图丢失 | 签名图先落 OSS，成功后再写库；失败回滚事务 | Service |

## 3. 需求 B：标的推荐给投资人

### 3.1 现状

- 无推荐代码。`lend` 9 条、`lend_item` 8 条（数据量小，协同过滤效果有限，但**教学演示足够**）。
- 文档提到的 Item-CF 未实现 → 本方案**分两级交付**，P1 先落地可用，P2 做亮点。

### 3.2 P1 规则打分推荐（必做，1 天）

**打分公式**（归一化后加权，分数越高越靠前）：

```
score = 0.35 × 收益分 + 0.25 × 期限匹配分 + 0.20 × 募集进度分 + 0.20 × 热度分
```

| 维度 | 计算 | 设计意图 |
|------|------|---------|
| 收益分 | `(lendYearRate - 5) / (14.6 - 5)` | 利率越高越推荐 |
| 期限匹配分 | `1 - |lend.period - 用户历史平均期数| / 36` | 贴合用户既有偏好；无历史则取 0.5 |
| 募集进度分 | `1 - investAmount/amount` | 剩余越多越靠前 |
| 热度分 | `investNum / max(investNum)` | 冷启动兜底，避免新用户无推荐 |

**硬过滤（必须满足才进候选）**：
- `status = 1 募资中`
- `investAmount < amount`（未满标）
- `lowestAmount ≤ 投资人可投能力`（可用余额）
- `lend.userId ≠ 当前用户`（不能推自己的标）
- 用户已投标的标的排除（不重复推）

**冷启动策略**：新投资人无投资历史 → 期限匹配分取固定 0.5，排序退化为"高收益 + 热门"混合，效果可接受。

### 3.3 P2 Item-CF 协同过滤（进阶，1~2 天，答辩加分项）

**原理**：把 `lend_item` 的 (投资人, 标的) 当隐式评分矩阵（投过 = 1，没投 = 0，可加权投资金额）。

```
Step 1  构建 user-item 矩阵
Step 2  计算 item-item 余弦相似度
              sim(i,j) = |U(i) ∩ U(j)| / sqrt(|U(i)| × |U(j)|)
Step 3  对用户 u 投过的每个标的 i，累加相似度打分
              score(u, j) = Σ  sim(i, j)     （j 不在 u 的已投集合中）
Step 4  取 TopN，与 P1 规则分做加权融合（规则 0.4 + 协同 0.6）
```

**实现位置**：`service/strategy/impl/ItemCfRecommendStrategy.java`（项目已有 `service/strategy` 包结构，正好适配策略模式）

**当前项目契合度**：`lend_item` 8 条偏低。建议实训期间**先灌一批 `ww_bank` 模拟投资数据**（或写个测试数据脚本），让相似度计算有意义；数据量小时与 P1 规则分做冷启动兜底即可。

### 3.4 接口设计

| HTTP | URL | 入参 | 说明 |
|------|-----|------|------|
| GET | `/api/core/lend/auth/recommend` | `topN`（默认 5） | 首页/列表页"为你推荐"（需登录，未登录走热门兜底） |
| GET | `/api/core/lend/{id}/similar` | `topN`（默认 5） | 详情页"相似标的" |

> ⚠️ 注意：文档里的 `recommend` 路径在 `api/core/lend` 下，但 `LendController` 现有 `@GetMapping("/{id}")` 会**吞掉 `/recommend`**（Spring 会把它当 `{id}` 解析然后 `Long` 转换失败）。
> **必须把 `/{id}` 改成 `/{id:\\d+}`**（正则限定数字），否则新接口永远 404/500。这是本次最容易踩的坑。

### 3.5 缓存策略

```
Redis key: recommend:user:{userId}      TTL 30 分钟
失效时机: 标的 publish / 满标 / 流标 / 下架  →  批量清除 recommend:user:*
         用户完成一次投资                    →  清除该用户 key
```

## 5. 实施步骤（每步可独立验收）

| 步骤 | 内容 | 交付验收标准 |
|------|------|-------------|
| **S1** | 建 3 张表（`docs/contract.sql`）+ `Contract`/`ContractTemplate`/`ContractSignRecord` 实体、Mapper、Service；模板 CRUD 接口 | Knife4j 里能新增模板、分页查询；插入重复 `biz_type+biz_id+contract_type` 报唯一键冲突 |
| **S2** | `SignPad.vue` 组件 + 用户端 4 个接口 + `contract/my.vue`、`contract/detail.vue` | 手写签名 → 上传成功 → 合同状态变 `1已签署` → 列表可见签名图；重复签名被唯一索引挡住 |
| **S3** | 三处强校验插入：`publish()` / `buildInvestForm()` / `buildMakeLoanForm()`；标的一生成时预生成合同 | 未签时：标的发布被拒（提示明确）、投资被拒、放款被拒；签完后**全部放行** |
| **S4** | `/{id:\\d+}` 修正 + 规则推荐接口 + 缓存；用户端"为你推荐""相似标的"落地 | 推荐接口返回 TopN 且不含自己的标、不含已满标；冷启动（新用户）不报错 |
| **S5**（可选） | Item-CF 策略类 + 融合打分 + 测试数据脚本 | 相似度计算有产出；融合前后排序有差异可对比 |

**建议周期**：S1+S2+S3 各 1 天，S4 半天，S5 1~2 天 —— 共约 **4~5 天**。

## 7. 风险与坑（已预判）

| 风险 | 说明 | 对策 |
|------|------|------|
| `/{id}` 路径吞掉 `/recommend` | `LendController` 的 `@GetMapping("/{id}")` 会优先匹配 | 改成 `/{id:\\d+}`，**S4 第一步就做** |
| 签名图体积超限 | Canvas 默认 PNG 可能 200KB+，base64 再膨胀 33% | 前端压缩到宽 400px + `image/jpeg` quality 0.7；后端限制 2MB |
| `buildInvestForm` 加了校验导致老流程中断 | 已有投资人历史无合同，突然全部被拦 | 提供管理端"批量补签/豁免"开关，或对历史标的只提示不拦截（灰度） |
| 合同正文渲染 XSS | 模板变量含用户昵称等 | 前端渲染用纯文本插值（不用 `v-html`），或后端做 HTML 转义 |
| 协同过滤数据太少 | `lend_item` 仅 8 条 | S5 提供测试数据脚本；融合时给规则分兜底权重 |
| 事务边界 | 签名图上传是外部调用，不能包在 DB 事务里 | 先上传拿 URL，再开事务写库（与项目既有 `buildInvestForm` 同思路） |

## 9. 推荐能力可以铺到哪些地方（回答"还有啥可以推荐到"）

### 9.1 可推荐的对象 —— 除标的之外，本项目的数据模型还撑得起这些

| 1 | **标的**（已规划） | `lend` | 收益/期限/进度/热度加权 | 主场景 |
| 2 | **相似标的** | `lend` + `lend_item` | Item-CF 物品相似度 | 详情页承接，提高停留 |

| 4 | **可借额度 / 积分等级** | `integral_grade`、`user_integral` | 按当前积分匹配下一档等级 | 引导借款人提额、提认证 |
| 5 | **理财产品化的标的组合** | `lend` 聚合 | 按期限分层（短期/中期/长期）打包推荐 | 提升客单价 |
| 6 | **投资榜单 / 热榜** | `investment_list`（表已存在） | 按投资额/人数排序 | 冷启动兜底，零算法成本 |

### 9.3 推荐策略可叠加的维度

- **规则层**：收益、期限、起投金额、募集进度、热度（§3.2，已规划）
- **协同层**：Item-CF / User-CF（§3.3，已规划）
- **画像层**：风险偏好（历史平均利率）、活跃度、资产规模、是否新客
- **场景层**：新客专享、老客复投、高净值专属、流标后安抚再推荐
- **实时层**：Redis 特征 + XXL-Job 定时预计算（项目已有 `jobhandler`）

### 9.4 推荐的"配套工程"（容易被忽略但很影响效果）

| 能力 | 说明 |
|------|------|
| 推荐理由 | 「因为你投过『XX标』」「与你偏好期限一致」——显著提升点击率 |
| 多样性控制 | 同一借款人的标最多出现 1 个，避免推荐位被一家占满 |
| 去重 | 排除已投、已满标、已下架、自己发的标 |
| 冷启动 | 无行为新用户退化到「热门 + 高收益」 |
| 埋点与 AB | 曝光/点击/投资转化三埋点，按 userId 哈希分桶做 AB |
| 兜底 | 算法超时或异常 → 直接返回热门榜，**推荐位永远不能白屏** |

### 9.5 合同模块还可以顺手补的（成本低、收益明确）

| 能力 | 落地方式 |
|------|---------|
| **合同 PDF 下载** | 项目已引 `pdfbox 2.0.29`，直接把正文快照 + 签名图渲染成 PDF，无需加依赖 |
| 签署提醒 | 复用 `MessageService.send()`，合同生成后推站内信+短信 |
| 超时自动作废 | 复用 `FinanceJobHandler`（项目已有 XXL-Job），扫 `sign_deadline < now()` 的待签合同 |
| 合同验真页 | 输入合同编号 + 哈希片段，校验是否被篡改（对外展示平台合规能力） |
| 签署方二次校验 | 大额（如 ≥5万）要求短信验证码二次确认，与手写签名叠加 |
