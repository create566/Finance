## 一、网关（finance-gateway）到底是什么

一句话：**网关是给前端用的「唯一门牌号 + 总机」。**

没有网关时，前端必须知道每个后端服务各自的端口（8990 是业务、8130 是文件、8081 是 AI），
端口一变前端就得跟着改；有了网关后，**前端只认识 8088 一个地址**，
请求带什么路径、由网关决定转发给谁：

```
浏览器  →  vite(5174/5173)  →  网关 8088  →  service-core / service-oss / service-sms / AI
```

打个比方：网关就是公司的**总机**。你只拨总机号，报「我找财务」，
总机帮你转接；财务换办公室（端口变了）你也不用知道。

**它带来的三个实际好处：**

1. **前端解耦** —— 前端只配一个地址，后端换端口/加服务都不用改前端。
2. **统一入口** —— 跨域、鉴权、限流、日志可以集中在网关做一次。
3. **服务发现** —— 网关从 Nacos 拿服务实例列表（`lb://service-core`），
   后端多开一个实例就自动分担流量，不用改任何配置。

**它不做什么**：网关不写业务逻辑、不碰数据库。业务全在各子服务里。

## 三、本次改动（2026-10-08）

### 1. 删除 api 里重复的文件上传控制器

- 删除 `api/.../controller/api/OssFileController.java`。
- 理由：它与 `finance-oss` 的 `FileController` 是**同一个 HTTP 契约**
  （`POST /api/oss/file/upload` + `DELETE /api/oss/file/remove`），而 api 那版是**真子集**
  ——只收图片、不收 `category` 参数；oss 那版额外支持 pdf 与自定义文件名。
  前端只传 `file`，两版都能接 ⇒ **删除不丢任何功能**。
- **保留** api 的 `FileStorageStrategy` / `LocalFileStorageStrategy`。
  它们仍被 api **进程内**调用，属 api 自己的业务副产物，不是文件服务：
  - `ContractServiceImpl:278` —— 合同签署时把签名图落盘；
  - `KnowledgeDocServiceImpl:129/180` —— 知识库 PDF 上传/删除。
  把这两个也搬到 oss，会让**合同签署变成 oss 的硬依赖**（oss 挂了就签不了合同），得不偿失。

### 2. 网关新增 `/api/knowledge/files/**` 路由（**不要删**）

- 背景：改造前 api 上传的文件 URL 前缀是 `/api/knowledge/files/...`，
  且**已经入库**：`investor_attach.image_url`、`contract_sign_record.sign_img_url`
  （实测样本如 `/api/knowledge/files/images/images_1790563059470_9942.png`、
  `/api/knowledge/files/signatures/signatures_1790753808218_9983.png`）。
  前端是直接 `<el-image :src="该 URL">` 渲染的。
- 风险：前端改走网关后，若没有这条路由，这些历史图片**全部 404**
  （而前端直连 8990 时完全看不出来，属于典型「切入口才暴露」的问题）。
- 解决：新增路由把该前缀转发回 `service-core`，由 api 的静态资源处理器提供文件。
  这些文件是 api 落盘的业务副产物，**由 api 提供在架构上是正确的**。

### 3. 前端代理改指网关

- `ww_finance_user/vite.config.ts`：`/api`、`/ai` 由 `8990`/`8081` 改为 **`8088`**。
- `ww_finance_admin/vite.config.ts`：`/admin`、`/api`、`/ai` 全部改为 **`8088`**。
- 保留 `VITE_API_TARGET` / `VITE_AI_TARGET` 环境变量作为**绕过网关的排障出口**
  （如 `VITE_API_TARGET=http://localhost:8991` 起隔离实例自测）。
- 效果：网关从「一条没人走的路」变成**真正被使用的入口**。

### 4. 一个顺带的安全修复（上一轮已做，此处记录）

api 原 `JwtAuthInterceptor` 每请求把 `Authorization` 头**原文**（完整 token）打进日志 = 凭证落盘；
现改为只记录「是否携带 token」。

## 四、启动顺序

```
1) Nacos          8848        D:\nacos\nacos-dist\nacos\start-standalone.bat
2) MySQL/Mongo/Redis/Chroma   本机服务 + docker compose up -d
3) 银行 jar       9090        ./run_bank.sh
4) api            8990        （需 1、2、3）
5) finance-message 8120       （需 1、2）
6) finance-oss    8130        （需 1、2 —— Nacos 与 Redis）
7) finance-gateway 8088       （需 1，以及 4/5/6 已注册才有意义）
8) finance-ai     8081        （需 2）
9) 两个前端       5173/5174   npm run dev
```

**启动依赖要点：**

- `finance-gateway` / `finance-oss` **没有 Nacos 会启动直接失败**（注册失败即终止 Spring 上下文），
  不是「起来但路由无效」。
- `finance-gateway` / `finance-oss` 的配置里**不要写 Nacos 账号密码**：
  本机 Nacos `nacos.core.auth.enabled=false`，任何凭据都无法登录，
  配了只会每 2 秒刷 `SecurityProxy login ... failed` 的 ERROR 日志。注册走免鉴权 v1 OpenAPI，正常。
- ⚠️ 注册 IP 会取到虚拟网卡（实测 `192.168.112.1`）。**同机访问正常，换机部署会失效**；
  要确定性可给各服务加 `spring.cloud.nacos.discovery.ip: 127.0.0.1`。

### 文件上传链路（经网关，两个真实用户 token）

| 步骤 | 结果 |
| --- | --- |
| user42 上传 | 200，URL = `/api/oss/file/images/u42/images_...png`（**属主编进路径**） |
| 无 token 上传 | 401 `{"msg":"缺少认证token"}` |
| 经网关取回该文件 | 200，**53019 字节 / md5 与源文件完全一致** |
| user43 删 user42 的文件 | `{"msg":"无权删除该文件","code":403}` |
| user42 删自己的文件 | 200 `删除成功` |
| 删除后再取 | 404（文件确已消失） |

> 注：本项目 `PccAjaxResult` 的业务码写在 JSON 里（`code`），HTTP 状态恒为 200。
> 判据看 `code`，不要看 HTTP 码。

## 六、遗留（不影响当前功能）

1. **两套文件 URL 前缀并存**：历史文件 `/api/knowledge/files/...`（api 提供）、
   新上传 `/api/oss/file/images/...`（oss 提供）。两者写的是**同一个物理目录**
   `uploads/`，只是 URL 前缀不同，不构成数据分裂。
   若要统一，需要一次性迁移库中历史 URL，属独立任务。
2. `finance-ai` 未注册 Nacos，网关对 `/ai/**` 是直连 `http://localhost:8081`。
   要彻底「微服务化」需给该模块加 Nacos 依赖并改路由为 `lb://service-ai`。
3. `BankBindTest` 有 2 个**陈旧断言**失败（与本次改动无关）：
   ① `testBankBindFlow` 自签 token 后从不写 Redis，而拦截器要求 token 与
   Redis 值完全相等 ⇒ 恒 401；② 期望响应体 `sign error`，而生产端早已改为 `success`/`fail`。
