## 第五轮复核（2026-10-10 16:45）— 「出借成功 → 返回平台 → 掉登录页」+ 收银台占满当前窗口（**已修复**）

> 触发场景：投标点「确认投资」后跳到银行收银台，「出借成功 → 点击返回平台」**落在登录页**。
> 用户诉求原文："点击返回平台进入了登录页面，不能再开一个窗口吗？"

**根因（两条叠加）**：

1. **回跳地址写死到 `/home`**。投标/还款/充值/提现/绑卡/放款六个入口的回跳都由
   `HfbConst.*_RETURN_URL = frontBaseUrl + "/home"`（`HfbConst.java:119-139` 原实现）生成，
   而 `/home` **不在用户端路由守卫的白名单**里（`ww_finance_user/src/route/index.ts:4` 只有 `/login`、`/register`）。
   银行回跳是**一次全新的整页加载**，登录态 `user_token` 又是**按 host 存**的 cookie
   （`utils/request.ts:11`、守卫 `getToken()` 同源读取）。当用户用 `http://127.0.0.1:5174` 访问、
   而配置 `BANK_FRONT_BASE_URL` 是 `http://localhost:5174`（或改用 IP / 域名而配置没跟着改）时，
   **host 一变 cookie 就带不过去** ⇒ 守卫执行 `next('/login')`。这就是"钱都付了反而退登"。
2. **收银台表单走「当前标签页整页跳转」**。`invest/detail.vue#submitInvest:152-166`、
   `borrow/repay.vue#handleRepay:68-77` 都是 `document.body.appendChild(form); form.submit()`：
   一跳走整个 SPA 被卸载，用户停留在银行页面的整段时间里应用"消失"，回跳再叠加第 1 条。
   （对照：`account/overview.vue#submitBankForm` 早就用的 `window.open('','_blank')` —— 所以充值/提现没有这个问题。）

**修复**：

- **前端 `ww_finance_user`**：
  - 新增 `src/utils/bankForm.ts#openBankForm()` —— 银行收银台**统一在新窗口**打开，返回三态
    `opened | blocked | not-form`。`blocked`（浏览器拦截弹窗）时**故意不回退成当前标签页跳转**
    （那正是要修掉的问题），并让调用方**不谎报"成功"**；新窗口被关闭后回调刷新原页面数据。
  - `invest/detail.vue`、`borrow/repay.vue`、`account/overview.vue` 三处统一改走它。
    原标签页始终留在应用内 ⇒ 登录态与页面状态都不丢。
  - 新增**免登录**结果页 `src/views/bank/return.vue` + 路由 `/bank/return`（已加入 `route/index.ts` 白名单）。
    检测到 `window.opener` 即判定为支付新窗口，倒计时自动关闭；用户回到原标签页即见最新余额/进度。
  - 「签完协议自动续投」这条链路没有用户手势、弹窗可能被拦，已把引导改成交互式
    （金额保留，提示"点击《确认投资》重新发起"），不再静默失败。
- **后端 `api`**：`HfbConst` 新增常量 `RETURN_PAGE_PATH = "/bank/return"`，
  六个 `*_RETURN_URL` 由 `frontBaseUrl + "/home"` 改为 `frontBaseUrl + RETURN_PAGE_PATH`；
  `HfbConstTest` 同步收紧为"6 个回跳一律指向免登录结果页"（4 用例全绿）。

**交付**：重新打包 `api-1.0-exec.jar`（75,486,888 B，16:43）替换进 `D:\桌面\实训jar包`，
旧包备份 `api-1.0-exec.jar.bak_20261010_1643`。已核验 jar 内 `HfbConst.class` 含 `/bank/return`、不含 `/home`，
且第一轮修复的 `expireStalePending` / `existsSucceededByTransNo` / `releaseStalePendingFlows` 仍在。

⚠️ **部署提醒（本轮踩的就是这个）**：`BANK_FRONT_BASE_URL` 必须等于**用户实际访问的 host**。
本项目当前有两条访问路径：
- 本机直连 `http://localhost:5174`（或 `127.0.0.1:5174`）—— 默认配置正好匹配；
- 公网 `http://120.26.132.5:81`（阿里云 nginx → frp → 本机 Vite 5173/5174，见当天日志"公网 frp 访问"一节）。

公网用户访问时，若 `BANK_FRONT_BASE_URL` 仍是 `http://localhost:5174`，银行回跳会打到
**用户自己电脑的 localhost:5174**（那里什么都没有），而 cookie 也带不过去 ⇒ 表现为"掉登录页 / 打不开"。
⇒ 公网演示前须把 `BANK_FRONT_BASE_URL` 设成 `http://120.26.132.5:81` 并重启 api：
`export BANK_FRONT_BASE_URL=http://120.26.132.5:81`。
免登录结果页解决的是"回跳不再因缺 cookie 而掉登录页"；**跨 origin 的 host 不一致属配置问题，代码修不了**。

## 第四轮复核（2026-10-10 16:20）— 「在途占位流水」无兜底 ⇒ 可用额被永久占死（**已修复**）

> 触发场景：用户 100（张刚，`invest_auth_status=2`）账户里 ¥13000，投标却提示
> 「可用余额不足，本次需 ¥10000.00，当前可用 ¥0.00，还差 ¥10000.00，请先充值。」

**根因**：可用额算式是 `银行账户 amount − Σ(status=0 且 trans_type∈{提现2,投标3,还款6})`
（`BankAccountSyncServiceImpl.getAvailableBalance`）。而「投标 / 还款 / 提现 / 充值」都在
**生成银行收银台表单的那一刻**就落一条 `status=0` 占位流水（`LendItemServiceImpl:252`、
`LendReturnServiceImpl:700`、`UserAccountServiceImpl:109,156`），只有银行异步回调 `settlePending`
才会结算释放。**若用户在前端点完投标、浏览器跳到银行收银台却没有在那页完成操作就返回了，
银行侧既没记账也没有回调，这条占位就永久挂着** —— 用户自己没有任何办法解开。

**实证（2026-10-10 直连两侧库）**：user 100 有两条悬挂占位且**银行侧无对应记录**：

| trans_flow.id | 类型 | 金额 | status | create_time | 银行 `user_invest` 是否有对应 agent_bill_no |
| --- | --- | --- | --- | --- | --- |
| 32 | 投标 | 10000.00 | 0 处理中 | 16:04:27 | **无** ⇒ 资金从未移动 |
| 34 | 投标 | 1000.00 | 0 处理中 | 16:10:51 | **无** ⇒ 资金从未移动 |

⇒ 可用额 = 13000 − 11000 = 2000；16:04 时仅 id32 存在，故 10000 − 10000 = **0**（即用户看到的报错）。
**这与 P1-7（用户 33 那 6 条）是同一根因**，只是当时只清了数据、没堵源头。
另注：前端 `detail.vue#submitInvest` 拿到 HTML 就 `form.submit()` 跳银行页，
而 `resumePendingInvest` 在回跳后还会再触发一次 ⇒ **一次投标可能落 2 条占位**（id34/id35 相隔 6 秒即此故）。
**（"当前标签页整页跳转"已于第五轮改为新窗口打开：详情页不再被卸载，这类因回跳重进页面而重复下单的路径随之消失。）**

**修复（两层）**：
1. **数据一次性释放** —— `sql/fix_stale_pending_flows.sql`（备份 + 把「生成超 3 分钟仍处理中」的扣款类流水置失败，幂等）。
   执行后 user 100 在途占额 **0**、可用额恢复 **13000**。
2. **代码兜底（`api`）**：
   - `TransFlowService#expireStalePending(timeoutMinutes)`：把超时仍 `PROCESSING` 的扣款类流水置 `FAILED`；
   - `FinanceJobHandler#releaseStalePendingFlows`：`@Scheduled(cron="0 */5 * * * ?")`，阈值取
     `job.pending-flow.timeout-minutes`（默认 10）；
   - **`existsSettledByTransNo` → `existsSucceededByTransNo`**：幂等判据由"非处理中"收紧为"仅成功"，
     否则占位被置失败后、迟到的银行成功回调会被误判成重复通知而丢弃 ⇒「银行扣了钱、平台不入账」；
   - **置失败为何安全**：可用额真源始终是银行账户余额，占位只是"这笔还在路上、别重复花"的并发预留；
     钱真被划走时银行余额已经扣掉，没被划走时这笔预留本就该放开。

**交付**：新 `api-1.0-exec.jar`（75,486,864 B，16:20）已替换进 `D:\桌面\实训jar包`，
旧包备份 `api-1.0-exec.jar.bak_20261010_1621`。

### P0-1 银行侧 3 个账户余额为负 —— 【已修复 2026-10-08，平台侧统一可用额口径 + 在途占位 + 对账兜底】

> ⚠️ 修复范围说明：本条修的是 **"防新增"**（平台侧不再发出会导致透支的扣款请求）
> ＋ **"可发现"**（每日对账把负余额账户显式记进 `reconciliation_record`）。
> **存量 3 个负余额账户未做数据订正** —— 那是数据运维动作，需要业务先确认每笔的来龙去脉。
> 银行 jar 无源码，**银行侧仍无余额校验**，这是本条无法彻底闭环的根本约束。

**现象**：RDS `ww_bank.user_account` 共 139 个账户，其中 3 个余额为负：`-100.00`、`-650.60`、`-1,308,223.87`。
2026-10-08 复核另发现 1 个 **冻结额为负**（`1676.45 / -500.00`），合计 **4 个异常账户**。

**证据（字节码）**：银行 `UserAccountServiceImpl.transferAccounts()` 对目标账户做**无条件加减**：

```
amount = BigDecimalUtil.add(amount, amt)   // 或 subtract，取决于 amt 正负
return 0;                                  // 永远成功，没有余额判断
```

**根因**：银行侧扣款**不校验余额**。平台侧 `BalanceGuard.require(action, available, required)`（`api/src/main/java/com/example/demo/utils/BalanceGuard.java:32`）只在"生成表单前"读一次银行余额，挡不住并发提交、重复回调、回调重放。

**影响**：账实不平；一旦并发或重放，可产生负余额（资金凭空被扣）。

### P0-2 平台服务费整条链路不通 —— 【暂缓】按"银行返点"模式不在此处实现

> **处置结论（2026-10-08 确认）**：平台的收益模式是**银行返点**，不是向用户计提服务费。
> 因此本项**暂不按"补 `mchFee` / 计提 `fee`"的方向整改**，保留现状。
> 但由此派生出一条新的硬性要求 —— **每一笔与银行的往来都要有日志**，以便后续与银行对账
> （见 P0-5，已实施）。⚠️ 唯一需要在动放款代码时留意的遗留风险：`mchFee` 缺失导致的 NPE 依旧存在，
> 只是当前放款链路本身未闭环，暂未触发。

**现象**：银行侧 `user_return.vote_fee_amt`、`user_invest.vote_fee_amt`、`user_item_return.fee_amt` 全为 0；平台 `lend_return` 48 行 `fee` 全 0。

**证据（逐条）**：

| 位置 | 内容 |
| --- | --- |
| `LendReturnServiceImpl.java:289` | `lr.setFee(BigDecimal.ZERO);` |
| `LendReturnServiceImpl.java:327` | `lir.setFee(BigDecimal.ZERO);` |
| `LendReturnServiceImpl.java:436` | `paramMap.put("voteFeeAmt", lendReturn.getFee() != null ? lendReturn.getFee() : BigDecimal.ZERO);` → 恒为 0 |
| `LendItemServiceImpl.java:200` | `paramMap.put("voteFeeAmt", "0");` |
| 银行 `UserInvestServiceImpl.makeLoan` | `mchFee = new BigDecimal(map.get("mchFee"))` —— **无默认值** |
| `db_init.sql:166`、`sql/lend.sql:13`、`sql/fix_lend_tables.sql:23` | `service_rate decimal(10,2) COMMENT '平台服务费率'` |
| `Lend.java:45-46` | `@TableField("service_rate") private BigDecimal serviceRate;` |

**关键结论**：`lend.service_rate` **全项目零业务引用**（只在 DDL 与实体定义出现），是一个死字段；平台代码中**不存在 `mchFee` 字面量**，即从不传该参数。

**银行侧收费的两个入口（字节码确认）**：
1. **放款** `makeLoan`：解冻各投资人 `voteAmt` → 读 `mchFee` → `transferAccounts(借款人, ΣvoteAmt − mchFee)`，即"砍头息"式收取。
2. **还款** `returnCommit`：逐条 `transferAccounts(投资人, transitAmt)` → 强校验 `voteFeeAmt + ΣtransitAmt == totalAmt` → `transferAccounts(借款人, "-"+totalAmt)`，`voteFeeAmt` 即平台服务费。

**影响**：
- 平台商业模式（赚服务费）在当前代码下**完全未落地**，一分钱收不到。
- 更危险的是**执行顺序**：`makeLoan` 先解冻投资人资金，**再**读 `mchFee`。平台从不传该参数 → 解冻完成后抛 NPE，资金已解冻但放款未完成，留下悬挂状态。

**整改建议**：
1. 明确费率来源：启用 `lend.service_rate`（或在平台配置中新增费率），在发标/投标时写入 `lend_item`。
2. 放款表单补 `mchFee` 字段，取值 = `ΣvoteAmt × service_rate`（或按产品约定）。
3. 还款侧把 `fee` 落成平台服务费（即 `voteFeeAmt = 本期服务费`），同步修 `LendReturnServiceImpl:289/327` 两处硬编码。
4. 平台侧需建"服务费应收/已收"台账，因为银行侧只留痕不划转，钱实际留存银行清算账户，靠线下结算。

**验收**：跑一笔完整放款+还款，银行 `user_return.vote_fee_amt` 与 `user_invest.vote_fee_amt` 非 0，且平台 `lend_return.fee` 非 0。

### P0-3 银行无"放款回调"，放款闭环断裂 —— 【已修复 2026-10-08，改为服务端同步放款】

#### 根因（2026-10-08 javap 反编译 + 实测定性，**五层叠在一起**）

1. **银行的放款接口是同步 JSON，根本不发回调。**
   `com.heepay.controller.UserInvestController.AgreeAccountLendProject` 返回 `Map<String,Object>`
   （`@ResponseBody` JSON），字节码里**没有任何异步通知调用** ——
   而绑卡/充值/提现/投标那几个 controller 都持有 `threadPoolExecutor` 用于回调，唯独放款这个没有。
   ⇒ 平台 `/api/core/lend/notifyMakeLoan` **永远不会被触发**，标的永久卡在 `status=2`（已满标待放款）。

2. **就算有人把银行应答喂给平台，也会被判成"失败"。**
   银行同步放款成功回 `resultCode=0000`；而平台 `handleMakeLoanNotify` 只把 `"0001"` 映射成成功
   （异步回调那套是 `"1"`/`"0001"`）⇒ `0000` 被当成"银行侧失败"，静默 `return true`，什么都不做。

3. **平台提交表单的浏览器链路只会拿到一段 JSON。**
   旧 `AdminLendController.makeLoan` 返回 `formHtml`，前端 `window.open().document.write(formHtml)`
   自动提交 → 浏览器拿到的是 JSON 文本，既没有银行页面也没有后续跳转，管理员看不出任何异常。

4. **银行侧必传 `mchFee`，平台从来没传 ⇒ 银行 NPE 500。**
   `UserInvestServiceImpl.makeLoan` 里 `new BigDecimal((String) map.get("mchFee"))` **无判空**，
   且在"解冻投资人资金"**之后**才执行 ⇒ 真要发也会把资金解冻了再炸。
   （注：幂等短路 `user_invest.status==1` 在 `mchFee` 之前，所以"已放款过的标的"反而不会 NPE ——
   这也是为什么历史上 4 个标能放款成功。）

5. **平台投标表单从来没传 `benefitBindCode` ⇒ 银行放款时对 `"0"` 划转失败。**（2026-10-08 实测发现，前四层修完后才暴露）
   银行 `makeLoan` 的资金去向来自 `user_invest.benefit_bind_code`：

   而 `user_invest.benefit_bind_code` 只在投标时由平台表单写入 —— 平台 `buildInvestForm()` **压根没有这个字段**，
   银行侧 78 条投标记录里 **11 条是 `"0"`**（其余靠历史数据碰巧有值）。
   ⇒ 实测表现：银行返回 **HTTP 200 + 一段"出错了"的 HTML**（不是 JSON），平台解析失败报"银行无应答"。

### P0-4 逾期还款与银行强等式校验冲突

⇒ 详见 **P4-53**（已单列，影响面比本条更大：P2P 标的多半是多投资人）。

1. 首选：把罚息计入 `voteFeeAmt`（即 `fee = 罚息`），使等式成立——代码注释本身也写"罚息部分归平台"，正好与 P0-2 的服务费计提合并实现。

### P0-5 银行往来无对账日志，失败回调静默无痕 —— 【已修复 2026-10-08】

**修复前的三个缺口**：

1. **6 个回调全部静默**：`BankNotifyController` 只回 `"success"` / `"fail"`，不记任何日志。
   Service 的失败分支（验签不过 / `resolveNotifyUser` 返回 null / 金额异常）一律 `return false`，
   从现象上分不清是哪种原因 —— 而银行会**永久重试**，问题却查不到。
2. **出站请求无记录**：平台生成银行表单后由**浏览器**提交，服务端没有任何出站记录。
3. **对账无痕**：`reconciliation_record` 只在**有差异时**落库，银行流水为空时直接 return
   → 表里 0 行，**无法区分"没差异"和"没跑过"**。

**修复方案（只加日志，零行为变更）**：

| 新增/改动 | 内容 |

  `LendItemServiceImpl.java:385-401`（`cancelInvest`）与 `LendServiceImpl.java:215-233`（`withdrawAllInvestments`）

  而投标回调 `LendItemServiceImpl.java:482` 却执行了 `updateBalance(user, INVEST, amount)` 从 `user_account` 扣减。
  ⇒ 任一次流标 / 下架 / 撤标后，相关投资人的平台镜像余额**永久偏低**（银行侧已解冻，平台侧没加回）。
  连带影响：`RecommendServiceImpl` 读该镜像做"可投能力"过滤，会误判余额不足而过滤推荐。

- **P4-20【高】投标回调满标判断未判空**

  且 `LendItemMapper.atomicInvest` 是 `invest_amount = invest_amount + ?`（NULL 加任何数为 NULL）。
  ⇒ 一条 NULL 数据即让该笔回调 NPE —— 投资人资金已冻结，平台却不入账、不生成投资记录。

- **P4-21【中】镜像扣款失败会抛异常打断银行回调**
  `UserAccountServiceImpl.java:229-233`：`updateBalance` 扣款不足时 `throw new BusinessException(400, ...)`

  投标/还款的**银行回调**会在 `updateBalance` 处抛异常 → 回调整体失败 → 银行无限重试，而资金在银行侧已动。

- **P4-22【中】对账响应用手写字符串切分解析 JSON**
  `BankAccountSyncServiceImpl.java:206-217`（`parseBankResponse`）与 `:222-240`（`parseBankFlowResponse`）

  键值即错位 → 对账金额比对错误、差异记录失真。**这是对账可信度的直接威胁**，建议改用 Jackson 解析。

- **P4-42【高】`auditBorrowInfo` 自调用导致审批流程完全没有事务**

### P5 · 数据库结构与脚本漂移（新增 9 条，实测 `information_schema`）

> 根因：`db_init.sql` 用 `CREATE TABLE IF NOT EXISTS`，遇到已存在的老表直接跳过 ⇒ **脚本从未在该库真正跑全**，
> 于是"库"与"脚本"长期分叉。实证：库里现有 `investment_list` 这张表，**任何脚本里都没有**。

- **P5-23【高】字符集退化：16 张表是 `utf8mb3`，脚本全写 `utf8mb4`**
  实测 `utf8mb3` 表数 = **16**（`user`/`lend`/`lend_item`/`lend_return`/`borrow_info`/`trans_flow` 等全部主表）。
  ⇒ 向这些列写 4 字节字符（emoji、部分生僻字）直接 `Incorrect string value` → 接口 500。
- **P5-24【高】金额列被压成 `decimal(10,2)`（上限 99,999,999.99），脚本写的是 `decimal(20,2)`**
  实测 `lend.amount`、`lend.invest_amount` 均为 `decimal(10,2)`。⇒ 金额 ≥ 1 亿时报 `Out of range` → 500。
- **P5-25【中】`lend.risk_level` / `lend.money_use` 在库里根本不存在**（实测命中数 = 0），
  但 `db_init.sql:171/173`、`sql/lend.sql:16/18`、`sql/fix_lend_tables.sql:26/28` 都在建；
  且 `AdminLendController.java:157` 仍在读请求参数 `riskLevel` → **风险等级/资金用途永远静默丢弃**。
- **P5-26【中】`lend_item.status` 库里 `tinyint NULL DEFAULT NULL`，脚本写 `NOT NULL DEFAULT 0`** ——
  这是 **P1-5 / P1-6 的根因**：凡是"不显式赋值、指望数据库兜底为 0"的写入会落成 `NULL`，
  使 `status IN (0,2)`（退资查询）整行漏掉。
- **P5-27【中】5 处唯一约束只存在于库里、脚本未声明**：
  `user_account.user_id`、`borrower.user_id`、`user_bind.user_id`、`lend_return.return_no`、
  `dict.(parent_id,value)`。⇒ 按脚本重建库后这些唯一性全部消失，并发写入可产生
  "一个用户多条账户 / 多条绑卡 / 重复还款编号"，余额与退资会被分散到错误行。
- **P5-28【中】`borrow_info.borrow_year_rate` 库 `decimal(10,2)` vs 脚本 `decimal(10,6)`** → 利率小数位被截断。
- **P5-29【低】`investment_list` 是"库里有、脚本无、Java/XML 零引用"的死表。**
- **P5-30【低】实体 `KnowledgeDoc` 缺 `file_url` 字段（库里有该列）、`fileSize` 是 `Long` 而库列是 `int`。**
- 另有一批**列长度 / 可空 / 默认值 / 列顺序**漂移（`user.*`、`lend.*`、`lend_item.*`、`lend_return.*`、
  `trans_flow.*`、`user_bind.*`、`borrower.*`、`dict.*` 共约 8 组），不逐一列出，建议统一用
  `information_schema` 与脚本做一次机器比对并重新生成 `db_init.sql`。

## 附：已证伪的两个误判（避免再犯）

| 曾经的判断 | 事实 |
| --- | --- |
| `status=4` 是"已满标待放款" | ❌ `4` 是**已下架（OFFLINE）**，`2` 才是已满标待放款。`LendStatusEnum`：0待发布/1募资中/2已满标/3已逾期/4已下架/5还款中/6已完结/7已流标 |
| "逾期扫描任务没生效" | ❌ 直查 `lend_return` 无任何 `status=0 AND return_date < CURDATE()` 的记录 —— 逾期任务只是**暂时没有对象**（首期 10-11 才到期），不是失效 |

另：`lend_return` 的逾期列名实为 `is_overdue`（不是 `overdue`）。
