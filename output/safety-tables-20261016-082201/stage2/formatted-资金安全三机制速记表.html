  一句话总纲：入口幂等保不重、并发原子保不超、事后对账保不漏。三层各自独立兜底，且每层都有落库痕迹可查——「钱不会错」不靠承诺，靠机制。

  速记口诀：回调重复莫重复，只认成功再入账；累加必带额度条件，撤资先过 CAS 闸门；对账每天心跳留一行，异常笔笔有留痕。

二、机制一：入口幂等（重复回调，不重复入账）

机制一要解决的问题：银行对同一笔回调可能重试推送多次，平台必须做到「重复通知、只入账一次」，同时不能把迟到的成功回调误杀。下面先记判据，再记实现。

（一）幂等判据（最核心的一张表）

同 transNo 流水的状态是否算「已入账」原因
成功是直接确认应答 success，不再入账
处理中否否则回调被误判为重复通知吞掉，那笔钱永远挂在处理中
失败否超时兜底会把占位置为失败，迟到的成功回调仍须能结算入账

（二）实现拆解

环节做法文件
统一出口6 类回调（绑卡/充值/提现/投标/放款/还款）统一走 respond()：先落一条 BANK_TRADE 对账流水，再调 Service，应答 success/fail；异常不吞、原样抛出让银行重试controller/api/BankNotifyController.java
幂等判据existsSucceededByTransNo：同单号且 status=成功才算已入账service/impl/TransFlowServiceImpl.java
回调流程验签 → 银行状态判断 → 金额正则校验 → bindCode 反查用户 → 幂等 → 入账TransFlowServiceImpl、service/impl/LendItemServiceImpl.java
单号口径充值/提现用平台发起时生成的 agentBillNo（发起即落处理中流水占位）；投标/放款/还款用银行流水号TransFlowServiceImpl#resolveTransNo
在途状态机savePending 占位（FAILED 可重激活为处理中）；settlePending 只从 处理中/失败 结算到终态，不含成功（防迟到的失败回调把成功翻回失败）TransFlowServiceImpl
超时兜底每 5 分钟扫描，超时的「处理中」扣款类流水（提现/投标/还款）置失败释放占额jobhandler/FinanceJobHandler.java

三、机制二：并发原子（条件更新，从机制上防超募）

机制二要解决的问题：多个投资人同时投标同一标的时，「查余额→改金额」的读-改-写会互相覆盖，造成超募或撤资重复退款。解法是把互斥交给数据库，用条件 UPDATE 一行定成败。

（一）核心 SQL（背这一条就够）

-- 投标累加：行锁 + 剩余额度双条件，rows=0 即拒（已满或不足）
UPDATE lend SET invest_amount = invest_amount + #{amount}, invest_num = invest_num + 1
WHERE id = #{lendId} AND is_deleted = 0 AND status = 1 AND amount - invest_amount >= #{amount}

（二）原子操作全家福

操作SQL 要点防什么文件
投标累加invest_amount = invest_amount + ?，条件 status=1 AND amount-invest_amount>=?超募mapper/LendItemMapper.java
撤标回减invest_amount = invest_amount - ?，条件 invest_amount >= ?回减成负、并发互相覆盖同上
退资闸门UPDATE lend_item SET status=1 WHERE id=? AND status IN (0,2)连点撤标/并发批量退资导致同一笔退款两次同上
镜像扣钱UPDATE user_account SET amount=amount-? WHERE user_id=? AND amount>=?余额扣成负数mapper/UserAccountMapper.java

（三）三层防线的定位（别搞混）

层是什么定位
下单前校验BalanceGuard.require 余额判定 + 可用额 = 银行余额 − 在途（提现+投标+还款）+ 落「处理中」流水占位防：友好提示，非互斥
回调原子更新atomicInvest 条件 UPDATE，由数据库串行化真闸门：从机制上防超募
Redis 剩余额度缓存buildInvestForm 入口快速拦截仅提示；代码注释明示真闸门在回调

  易错点：手写 SQL 里 is_deleted = 0 必须显式写——@TableLogic 只对 MyBatis-Plus 自动生成的 SQL 生效，漏写会让已逻辑删除的标的继续被累加募集额。

四、机制三：事后对账（逐笔核对，异常留痕）

机制三要解决的问题：前两层都挡不住极端并发与回调重放，必须有一道事后兜底。每天凌晨跑一次逐笔核对，有差异全部留痕、可追溯。

（一）流程拆解

步骤做法留痕去向
定时触发每天 03:30（cron）+ Redis 分布式锁，多实例只跑一个jobhandler/FinanceJobHandler.java#dailyReconciliation
拉流水银行当日流水 vs 本地 trans_flow，以 transNo 为 keyservice/impl/ReconciliationServiceImpl.java
逐笔比对金额一致=匹配；本地无=缺失（status=1）；金额不符=不一致（status=2，双方金额都记）；银行流水缺 transNo=单独计数不写库reconciliation_record 表
本地多出银行查无的本地流水同样记缺失同上
账实兜底扫银行侧负余额/负冻结账户，逐条落差异（RECON-NEGATIVE- 前缀）同上
心跳行RECON-HEARTBEAT-<日期> 一天一行，重复运行就地更新区分「没差异」与「压根没跑过」
对账日志每次对账落一条 RECON 到 logs/bank-trade/bank-trade.log（保留 90 天）utils/BankTradeLog.java

（二）为什么事后对账不可省

银行扣款类接口（冻结/提现/划转）不校验余额，前置闸门与回调原子闸门都挡不住极端并发与回调重放——库里已出现 4 个负余额/负冻结账户（−100、−650.60、−1308223.87、冻结 −500，2026-10-12 实测记录）即为实证。前置闸门是「防」，事后对账是「查」：防不住的，逐笔核对逐一发现、笔笔留痕到人。
